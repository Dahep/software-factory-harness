## Question

Factory's agent layer currently treats the harness around each agent as runtime-provided (OpenCode's prompts, tools, skills, plugins via the RuntimeAdapter), and its mining-to-skills story (closed/004) assumes mining upgrades skills & workflows with human approval. Google Research's **Harness²** ("Recursive Agent Harnessing for an Open World", [arXiv:2610.14224](https://arxiv.org/abs/2610.14224), [code](https://github.com/google-research/harness2), [project page](https://harness2.github.io), Apache-2.0, includes an **OpenCode executor**) makes the harness itself a first-class, self-improving artifact. Study it and extract what Factory should adopt, adapt, or avoid:

1. **The eight editable harness components** (system prompt, guardrails, memory, tool guidance, subagents, skills, scripts, plugins): is this taxonomy a good vocabulary for Factory's per-agent capability profiles (ticket 009's open decision) and for what "harness" means behind the RuntimeAdapter?
2. **Task-level recursion — Propose→Probe→Compose** without ground-truth verifiers: does this belong in Factory as an optional agent-team pattern (a "harness improver" role alongside implementer/reviewer), and how does it reconcile with Factory's deterministic-graph stance (closed/011) where the Go engine owns effects?
3. **Harnessing-level recursion — the improvement library + evidence-backed lessons / EXPERIENCE.md**: how does this compare to closed/004's mining-into-skills-with-approval design? Do its automated lesson adoption and evidence-linking patterns strengthen or conflict with that closed decision?
4. **Practical fit**: paper claims and their caveats (benchmarks, k-scaling gains; proportional token cost per recursion step), code maturity (3 commits, 20.5k stars), what running it against an OpenCode executor actually requires.

Verdict must state: concrete adopt/adapt/avoid recommendations per concept, which map tickets (006, 009, closed 004, closed 011) the findings touch, and whether any of them has a reason to re-open. Date every claim 2026-10-27 with sources.

### Comparison and analysis

#### Q1 — The eight editable components as vocabulary

The taxonomy is real, consistent across paper/README/release, and grouped by runtime role: **context construction** (C1 system prompt, C2 guardrails, C3 memory, C6 skills), **tool interface** (C4 tool guidance, C7 scripts), **orchestration** (C5 subagents), **middleware control** (C8 plugins) [2][3][4][5]. What makes it more than a slide deck is that the release maps each component onto **actual OpenCode slots** in `harness2/substrate/opencode.py`'s `OPENCODE_SURFACE` and the vendored baseline `harness.yaml` [6][7]:

| Component | File-level shape in the OpenCode executor |
|---|---|
| C1 system prompt | `systemprompt.md` — replaces the stock agent body (JB mode appends composed prose to `AGENTS.md`) |
| C2 guardrails | `guardrails.md` — always-on rules; also the autotrigger file for skill trigger lines |
| C3 memory | `LongTermMEMORY.md` — durable domain facts |
| C4 tool guidance | `tool_descriptions/tool_guidance.md` — prose about the toolset |
| C5 subagents | `sub_agents/<name>/AGENT.md` with frontmatter `mode: subagent` (→ `.opencode/agent/`), invoked via the `task` tool |
| C6 skills | `skills/<name>/SKILL.md` (→ `.opencode/skills/`), name must match dir, load-on-trigger via the `skill` tool |
| C7 scripts | `scripts/<name>.py` — deterministic helpers run via Bash |
| C8 plugins | `plugin/<name>.ts` (→ `.opencode/plugin/`) — hooks such as `tool.execute.after`, `chat.system.transform` |

The list is closed (K=8; the paper extends AHE's file-level decomposition by one component), and each component is *"mounted as a file in the runtime"*, so an edit is a diff [2]. Edits are plain in-place file edits by an LLM editor session (*"Your edits on disk ARE the proposal"*); a Python validator runs **before any rollout** — size cap, skill trigger line present, scripts compile, `mode: subagent` frontmatter, hook schema — with one retry, then inherit-the-starting-tree fallback [15]. The eight are also substrate-shaped: on Codex the four always-on files collapse into one `AGENTS.md` (8,000-char cap) and the middleware component becomes `.codex/hooks.json` [6] — the *roles* travel across substrates; the file paths do not.

Three boundary facts matter more than the list itself:

- **The taxonomy stops where the substrate starts.** The baseline manifest declares *"c2 context_policy: NOT injectable — OpenCode owns context assembly/compaction"*, and states OpenCode itself (CLI, tool implementations, provider) is *"FROZEN infrastructure"*, with the evolve loop restricted to files under the harness workspace [7]. (The same manifest also mislabels `guardrails.md` as `c6` — a labeling slip in the release, not a taxonomy claim.) A "harness" is therefore always "editable surface + frozen substrate", never everything.
- **Enforcement is asymmetric.** The plugin stub comment in the release says it plainly: plugins act inside the tool loop and are *"the only lever that can enforce something the model cannot skip"* [6]. Prose components (C1–C4, C6) shape behavior only if the model reads them; the substrate's `OPENCODE_PERMISSION` fence and output-token ceiling are the only hard limits [6]. `subagent_requires_mode=True` and `hooks_file=None` further show the surface is defined by what OpenCode actually supports [6].
- **The surface carries budgets and rules, not just files**: `always_on_max = 24_000` characters with the stated reason *"every token here competes with the agent's own output budget"*, skill-name matching, trigger-line conventions, and a `stubs` mechanism that teaches the improver how to add each component type [6].

**Verdict for Q1:** yes — adopt the eight components as Factory's vocabulary for what a harness *is* behind the RuntimeAdapter, but as a two-part contract: *(editable surface: the eight slots)* + *(frozen substrate: context assembly, compaction, provider, permissions)*, with an explicit **enforcement axis** (advisory prose vs. plugin/permission/approval-enforced) that the paper's taxonomy does not carry and Factory's capability profiles need.

#### Q2 — Task-level Propose→Probe→Compose vs. the Go-owned typed graph

The loop, from the primary text [2][10][11]:

1. **Reference**: 1 (k=1) or k executions of the current harness H₀ — *"The reference reveals how the harness behaves, not whether its deliverable is correct."*
2. **Propose**: two scoped editor sessions per candidate — an *invariant* editor (how the agent works: procedure, tool use, completion) and a *domain* editor (subject matter) — each editing the harness's component files, optionally reusing library components. *"No prompt names a rubric, score or grader; each states that no such thing exists in its context."*
3. **Probe**: each candidate executes the same task under matched model/environment; comparison with the reference yields a **behavioral contrast** that *"inform[s] subsequent composition rather than verify[ies] task correctness, as execution stochasticity and shared model biases limit the reliability of the evidence."*
4. **Compose**: k composition sessions (parallel) or chained steps (sequential) read the full evidence pool and combine only evidence-supported edits.
5. **Final selection** (k>1): an agentic selector compares **anonymized** deliverables and *"returns an existing output without access to its originating harness or synthesizing new content"*; the star in H* means *"adoption rather than verified optimality."* At k=1 selection is bypassed.
6. **Reflect** (harnessing-level, after deliverable return): updates the improvement library.

**Who owns effects:** all task side effects live in the executor rollouts, run in isolated staged workspaces; the improver sessions (editors, composer, selector, reflector) are read-only over recorded evidence plus harness-file edits; the library is fixed during a task and updated only after the deliverable returns [2]. Crucially, **Harness²'s own implementation is a deterministic scheduler around LLM sessions**: `schedule.py` runs "k shared reference executions → every mode → blind selection per mode → summary.json" with retries, resume, a per-session USD ledger, and the budget is documented exactly — *"Each mode schedules 4k rollouts and 3k improvement stages"* (`recursion.py`) and enforced as an asserted per-task identity in `ledger.py`: *"R = 4k: k shared base + 2k candidates + k finals"*, *"P = 3k: k INV + k DOM + k compositions"*, with selection and reflection recorded outside the ledger [10][11][15]. So k=1 costs 4 task executions (1 reference + 2 probes + 1 final run — matching the project page's illustrative case) plus 3 improver sessions and 1 reflector; k=5 parallel costs 5 references + 10 probes + 5 finals = 20 executions (5× k=1) plus 15 improver stages, 1 blind selection, 1 reflector [2][10][11].

**Reconciliation with closed/011:** no conflict — direct confirmation. The paper's system gives the same division of labor Factory's spec requires: a deterministic engine owns scheduling, isolation, retries, budgets, and adoption; stateless LLM sessions do bounded, evidence-bound work inside that graph. Propose→Probe→Compose fits the Go-owned typed graph as ordinary nodes: bounded fan-out over candidate harnesses → execute-in-scratch-workspace nodes → a compose node (pure function over recorded evidence) → a blind selection node → an adoption node that, in Factory, is an **approval gate**. The typed graph even expresses what the paper leaves as fixed config: k as a budget parameter, timeouts, retry policy, and spend caps.

**Where a "harness-improver" role sits in issue→triage→implement→review:** *outside* the per-issue loop, as a periodic/post-run maintenance workflow. Harness edits are cross-cutting — they change how every future run behaves — so they carry shared-state risk and must pass through review + human approval (closed/004's gate), exactly as Harness²'s own library is per-run scratch rather than shared infrastructure. Inside the issue loop, the useful residue is narrower: trajectory evidence gathering (what failed, which component was implicated) filed as evidence-linked candidates, and optionally a bounded arena-style *variant wave* for task-type-specific tactics whose output is a candidate harness diff for review — never auto-adopted. The invariant/domain editor split is worth keeping as a role distinction (ablation: removing scoping costs −2.9 points WB / −3.7 JobBench) [2].

#### Q3 — Harnessing-level recursion vs. closed/004: **upgrade, not conflict**

What the library actually stores (release + paper, [2][9]): per `(run, mode, domain)` — `INDEX.md`, and per adopted task `harnesses/<task>/harness/<rel>` (the **full adopted harness tree**) plus `harnesses/<task>/EXPERIENCE.md` with three fields required for admission, enforced in code: `cue`, `lesson`, `evidence` (plus `confidence` in the template) [9]. The reflector first marks each changed component with a verdict ∈ {helped, hurt, no observed effect, confounded} — *"'confounded' … whenever a candidate changed several components at once and no execution isolates them"* — and emits *at most one* durable entry per task [2][15]. Admission is evidence-gated: *"Lessons are retained only when supported by execution contrasts; selecting an output alone does not establish transferability"* and *"When evidence is insufficient, reflection adds no new experience entry"* [2]. The whole tree is carried into improver contexts, never a summary; grader verdicts are asserted out of context (`assert_tree_has_no_grader_verdicts`) [9].

Against closed/004's design (batch mining over transcripts → evidence-linked candidate learnings → reviewer waves → synthesis → **human approval** before skill/workflow edits):

- **Same epistemics, stricter and mechanizable.** 004 says never present inferred intent as ground truth and requires evidence links; Harness² hardens this into a machine-checkable admission rule (no execution contrast → no entry) and a fixed three-field lesson contract. That is a genuine upgrade to 004's candidate schema.
- **Artifact bundling is new.** 004's mining proposes *text* destined for skills; Harness² stores the **executable adopted artifact next to its why** — reusable components for direct reuse plus the experience guiding their application [2]. Factory should do the same: a candidate skill/workflow edit should carry the exact diff/config it came from.
- **Automated adoption is the one real conflict — and it is scoped away.** Harness² adopts without human approval because its library is per-(run, domain) scratch that resets every sweep (*"each sweep starts every domain empty"*, [9]). Factory's skills and workflows are shared and persistent across projects, so 004's approval gate stays. Adopt the *form* (evidence-gated, artifact-bundled, indexed retrieval), not the *governance* (auto-adoption).
- **Harness² concedes what 004/reflect already solve.** Appendix G lists library management — *"consolidate overlapping components, revise outdated experience, and refine retrieval"* — as future work [2]; the local reflect workflow's accepted/rejected/backlog synthesis with dedup into tracker issues already covers staleness and governance. Cross-run persistence is also absent in the release (roots are scoped per run/mode [9]) — Factory needs it and must design it.

**Verdict for Q3:** conflict = no; upgrade = yes, in four specifics (contrast-gated admission, `cue`/`lesson`/`evidence` contract, adopted-artifact bundling, index-on-demand retrieval), while keeping 004's human approval and multi-lens synthesis, and adding cross-run persistence/consolidation that Harness² explicitly leaves open.

#### Q4 — Practical maturity, cost, and honesty

**What the benchmarks measure** [2][4]: three professional benchmarks — WorkBuddy-Bench (office deliverables, Code/Web/Office domains; test halves 40/35/25), JobBench (65 professional job tasks, 34 in the frozen test split, long executions), Harvey's LAB (legal, 100-task held-out set; reported as `Partial`, the per-criterion pass rate) — graded by patched LLM-judge pipelines (WorkBuddy judged by Gemini 3.5 Flash, JobBench by Claude Opus 4.8, LAB by Claude Sonnet 4.6), across four executor configurations (Gemini 3.5 Flash / GLM-5 × OpenCode / Codex), means ± SD over three runs with shuffled task order. The default harness editor/selector is Claude Opus 4.8 under OpenCode — **which doubles as the JobBench judge, while Gemini 3.5 Flash both executes and judges WorkBuddy**: judge/executor non-independence is visible in the setup, alongside only three runs with no significance tests (e.g., Gemini/OC WB 77.5±2.5 vs Meta-Harness 76.4±0.7), author-reimplemented baselines, and failed judge runs recorded as unscored rather than zero [2][4][12]. Headline gains: **one step** up to +11.5 WB / +4.5 JobBench / +11.8pp LAB partial; parallel recursion adds up to +3.9 / +4.2 / +6.7 [2]. Flagship config (Gemini/OpenCode, WB): base 72.4 (0.9) → k=1 77.5 (2.5) → k=5 80.8; ablations at k=1 (WB): w/o library 74.4, w/o scoping 74.6, w/o composition 75.9 [2][3]. These are **LLM-judged single-deliverable office/legal/web tasks — not issue-driven software-engineering loops**; the deltas do not transfer to Factory's issue→merge milestone by assumption.

**Per-step cost, as the paper accounts it** [2]: Figure 6 counts *all tokens spent before the final deliverable* — execution plus improvement — and places both Harness² configs on the empirical Pareto frontier: k 1→5 lifts gains from +4.5→+7.5 (JobBench) and +5.1→+8.4 (WB) for Gemini/OpenCode, while Meta-Harness uses more compute than k=5 for lower performance. The paper publishes no raw numbers for Figure 6's axes; reading the rendered figure's log scale gives **approximate** tokens per task — WB base ≈0.45M → k=1 ≈2.5M → k=5 ≈12M; JobBench base ≈5–6M → k=1 ≈25–30M → k=5 ≈130–140M (eyeballed; no data table ships with the release) — i.e. k=1→5 costs ≈5× tokens, proportional to the code's asserted R=4k/P=3k identity [2][15]. Tables report `#Steps` (execution steps per task) beside scores; at k=1 the improved harness actually needs *fewer* execution steps than base on WB (avg 21.9 vs 25.4) even though total compute rises [2]. The release tracks per-session USD in its ledger and warns *"Model-backed runs incur API costs… review model pricing before launching a full run"* (LAB alone is 1,143 tasks) [11][12]. So the honest per-step framing: **k=1 ≈ 4× the executions of an unimproved run + 3 improver sessions; k=5 parallel ≈ 5× k=1** — "proportional cost per recursion step" is exactly right, and the paper says so rather than hiding it.

**Open-world honesty (quoted)** [2]: Appendix F — *"Harness² requires additional executions and editor sessions… Increasing the recursion budget therefore adds inference cost. Parallel sessions can reduce latency… but do not eliminate this additional computation"*; the trade-off is characterized *"over a bounded range of budgets rather than establishing a universally optimal allocation"*; execution-based feedback remains *"sensitive to execution variability and shared model biases. They do not guarantee correctness or establish that an adopted change will transfer to a different task."* Appendix G concedes fixed recursion budgets and unmanaged library growth. The README documents a contamination incident: *"In a validation run of this release, a Codex rollout on JobBench downloaded its task's rubric without being instructed to"* — and tells users to block egress to `huggingface.co`/`github.com` and report restrictions used [12]. Also notable: refining *without* reference/probes/library **degrades** WB Code 73.4→63.2 and Web 69.9→65.0 — the paper publishes its own negative result — and Appendix E.6 admits selection failures: *on WB-code an output scoring 55 is chosen over one scoring 95; on LAB, narrower coverage reduces the score from 54 to 26* [2]. This is unusually honest work for a v1 preprint.

**Code maturity** [4][13][14]: a squashed research release, not a maintained product — 3 commits, 134 unanswered open issues, a single 229-line test file holding five unit tests (all pass on Python 3.12.10, run 2026-10-27), no CI, and a packaging gap (README's `cp .env.example .env` references a file absent from the repo; the sdist's missing `third_party/` is tracked upstream as issue #144), benchmark runners vendored with provenance checks (`ASSETS.json` + `scripts/check_provenance.py`), thorough SETUP/EXPERIMENTS/BENCHMARKS docs, `--dry-run`/resume support, and a credentials-free `harness2-demo` that runs both recursion modes with deterministic editors. Stars (20.5k in three weeks) signal attention, not maintenance. Core Apache-2.0; the vendored pieces keep upstream licenses (Job-Bench eval, harvey-labs, workbuddy-bench, OpenCode's MIT) [4][8].

**What running it against OpenCode requires** [5][6][12]: a **pinned OpenCode source checkout at v1.14.18** (`anomalyco/opencode @ 23fb5e05…`, while the paper cites sst/opencode) fetched into `dependencies/` and run from source through **bun** (Node.js 20+; no `opencode` binary in the contract) with a 3-file compat patch (`provider/transform.ts` +3 lines, lockfile); three harness install modes (JB: `AGENTS.md` append + `.opencode/{skills,agent}` + scripts; WB: a home-dir Jinja `prompt.j2` ending in exactly one `{{ instruction }}` placeholder; LAB: workspace `opencode.json` tool gate); an `OPENCODE_PERMISSION` JSON fence allowing only the workspace plus `OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX=64000`; trajectories read from `opencode run --format json` JSONL, parsed **defensively because "the event schema varies by OpenCode version"**; Vertex AI credentials for the executors plus Anthropic credentials for the Claude Opus 4.8 editor; Docker (WB) and Pandoc/Poppler (LAB); and network restrictions against rubric leakage [6][12]. For Factory the reusable ideas are the **surface contract** (always-on files, skill/subagent/plugin dirs, trigger rules, context budget) and the **fence** — not the launcher, which is coupled to one pinned OpenCode version and an unstable event schema.

### Verdict — adopt / adapt / avoid

| Concept | Verdict | Reason |
|---|---|---|
| Eight-component taxonomy as vocabulary | **Adopt** | Maps 1:1 onto OpenCode's real slots in the release; the shared vocabulary 009 and the RuntimeAdapter both need. Ship it with two additions the paper lacks: a **frozen-substrate row** (context assembly, compaction, provider, permissions) and an **enforcement axis** (advisory prose vs. plugin/permission/approval-enforced). |
| Surface contract (`SurfaceSpec`: always-on files, dirs, trigger rules, 24k context cap, stubs) | **Adapt** | Becomes the RuntimeAdapter's editable-surface declaration for 006/009; keep Factory's own schema versioned rather than importing theirs. |
| Propose→Probe→Compose as an agent-team pattern | **Adopt as an optional, bounded graph pattern** | Evidence-based improvement without verifiers, and its own scheduler proves it composes with an engine-owns-effects stance. Express as typed-graph nodes (fan-out → scratch-workspace execute → evidence-only compose → blind selection → gated adoption) with k, retries, and spend caps as typed fields. Never on the issue loop's critical path. |
| "Harness improver" role | **Adapt — a separate maintenance workflow** | Harness edits are cross-cutting shared-state changes: run post-issue/post-run, produce evidence-linked candidate diffs, pass review + 004's human approval. In-loop use limited to evidence filing and bounded variant waves (arena-style), outputs never auto-adopted. |
| Invariant vs. domain scoped editor roles | **Adopt** | Measurably matters (ablation −2.9 WB / −3.7 JobBench unscoped); maps cleanly onto Factory's cross-project policy vs. per-project tuning [2]. |

| Improvement-library *form*: `cue`/`lesson`/`evidence` contract, contrast-gated admission, adopted-artifact bundling, `INDEX.md` on-demand retrieval | **Adapt into closed/004's mining** | Strict, machine-checkable upgrade to 004's candidate-learnings schema; store executable artifacts beside their evidence, not just prose. |

### Impacts on the map

- **006 — Decide harness substrate (open): touched; reshape, no re-open needed (it is already open).** Harness² strengthens the OpenCode side of the hybrid (closed/002 stands): it proves an external process can drive OpenCode as a fully editable, versioned artifact and shows the exact seam. Add two decision criteria to 006's grilling: (i) does the substrate expose a declared **editable-surface contract** (the eight slots) to the RuntimeAdapter, and (ii) what can the substrate **enforce** vs. merely prompt (H²'s answer: only plugins and permission config enforce). Also record the coupling cost H² pays — pinned source checkout, bun, compat patch, unstable event schema — as evidence for keeping runtime state behind the adapter.
- **009 — Decide capability control model (open): touched; reshape.** Use the eight components as the profile vocabulary for *what can be tuned*, and make the profile additionally declare *what is enforced* (permissions, always-ask approval, tool gates, spend/step budgets — including an always-on context budget à la the 24k cap) and *what is frozen* (context assembly, compaction, provider). Profiles then read as: editable slots (per role) × enforcement channel × frozen substrate × budgets — a concrete shape for the owner's "profiles + always-ask for high-risk" leaning.
- **closed/004 — Steer capture & mining with approval: touched; NO re-open.** Harness² strengthens rather than contradicts it (same evidence-first epistemics, stricter admission). Recommended amendment (small follow-up ticket, not a re-open of the verdict): add the `cue`/`lesson`/`evidence` lesson contract, adopted-artifact bundling next to lessons, the contrast-gated "no evidence → no entry" admission rule, and index-on-demand retrieval to the mining schema — while keeping human approval, reviewer waves, and adding the cross-run persistence/consolidation that Harness² leaves as future work.
- **closed/011 — Go-owned typed workflow graph: touched; NO re-open, no trigger fired.** PPC slots into the graph as bounded fan-out + scratch execution + evidence-only composition + blind selection + gated adoption nodes; the engine-owns-effects stance is *confirmed* by Harness²'s own deterministic scheduler around LLM improver sessions. Feed one item into the successor ergonomics ticket (per 011's own hand-off): expose candidate-fan-out and blind-selection as graph primitives, since arena-style waves and PPC both need them.
