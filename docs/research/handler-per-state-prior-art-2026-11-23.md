# Prior art: invoking typed per-state handlers with durable state

**Research date: 2026-11-23.** Every claim below is cited to a primary source (official docs, API reference, or first-party source) fetched on that date. Doc pages rarely show a "last updated" stamp; where one was visible it is given, otherwise the access date is the only date. Inngest, Argo, and the AWS pages are undated; Prefect's page reported `lastModified: 2026-11-19`; Cloudflare's retry page 2026-09-24 and metrics page 2026-11-10; Azure's storage-provider page `ms.date 2026-09-22`; Trigger.dev's task page 2026-11-12. Version anchors: Dagster docs "Latest (1.13.31)", Airflow stable/3.4.0, Temporal Go SDK v1.51.0.

This feeds the Factory rewrite's contract, failure-model, and events tickets (issues #10, #12–#16). Factory's decided model is unusual and the comparison is written against it: a user-authored, statically typed program with one re-entrant handler per state; the daemon persists state and re-invokes the handler for each transition; handlers perform direct side effects inside the Project VM and call an embedded library to dispatch agents and request infrastructure operations; Factory records an activation envelope per invocation and makes **no replay guarantee**.

## Verdict

The systems fall into three families, and none implements Factory's model exactly.

1. **Replay-from-start durable execution** — Temporal, DBOS, Restate, Inngest, Azure Durable Functions, Cloudflare Workflows, Trigger.dev, AWS Lambda durable functions. User code runs in a worker or the customer's app; the engine persists step results; after a crash the handler is re-entered from the beginning and completed steps are skipped by returning recorded outputs. This family has the strongest crash recovery and the sharpest rule: *only work inside a declared step is durable; everything else re-runs*. Its cost is determinism rules, replay-safe APIs, and versioning machinery.
2. **Engine-driven step machines with serialized I/O** — AWS Step Functions, Argo Workflows, Dagster, Prefect, Airflow. The engine owns the graph and invokes each step as a separate unit (Lambda, pod, process, task). Durable records are per-step state and I/O, not per-handler semantics; arbitrary side effects are invisible unless the step author records them. They give excellent operator views and poor typed-handler boundaries.
3. **Handler-per-activation without replay** — nothing in this survey. Azure Durable Functions is the historical handler-per-activation design, but it still replays. AWS Lambda durable functions comes closest at the contract level: it lets each step choose **at-least-once or at-most-once per retry**, which is the honest choice Factory needs for direct effects.

Factory should copy the *records, bounds, idempotency keys, and suspension tokens* these systems converged on, and avoid their replay machinery and their claims of exactly-once. No-replay is a legitimate design, but it moves the entire burden of resuming safely onto (a) the state the handler returns, (b) idempotency keys on mediated effects, and (c) an activation record detailed enough to reconstruct what happened without re-running it.

## Systems in detail

### Temporal

1. **Signature and payloads.** A Workflow is a function or method (`func YourBasicWorkflow(ctx workflow.Context) error`; Python `@workflow.defn` with `@workflow.run`). Activities are plain functions registered on a worker (`@activity.defn`). Arguments and return values "must be serializable" and cross the boundary as `Payload`s (binary data + key-value metadata) through a `DataConverter`; the default converter uses JSON, and a `PayloadCodec` does bytes-to-bytes transforms for compression/encryption. The docs explicitly recommend one object parameter rather than several: it keeps additive field changes from changing the signature, and several SDKs' type-safe start calls and the Web UI only accept one argument. ([workflow definition](https://docs.temporal.io/workflow-definition), [data conversion](https://docs.temporal.io/dataconversion), [activity definition](https://docs.temporal.io/activity-definition), accessed 2026-11-23)

2. **Invocation.** A Worker Process "poll[s] a Task Queue, dequeu[es] a Task, execut[es] your code … and respond[s] to the Temporal Service with the results"; workers are external to the service. The service records Commands emitted by the SDK and turns them into Events; the user's code never runs in the orchestrator. ([workers](https://docs.temporal.io/workers), [event history](https://docs.temporal.io/workflow-execution/event), accessed 2026-11-23)

3. **Crash detection, retries, idempotency.** The service cannot detect a lost task directly; it relies on Schedule-To-Start, Start-To-Close, and Heartbeat timeouts. Default Activity retry policy is initial 1 s, coefficient 2.0, max interval 100× initial, maximum attempts unlimited, no non-retryable errors; `ApplicationError(..., non_retryable=True)` opts out. Activities are at-least-once attempts: "Temporal guarantees that the Activity will be observed as completed exactly once. However, the Activity may be executed multiple times and may even partially complete more than once". The docs require idempotency and recommend a Workflow Run ID + Activity ID as the idempotency key. ([detecting failures](https://docs.temporal.io/encyclopedia/detecting-activity-failures), [retry policies](https://docs.temporal.io/encyclopedia/retry-policies), [activity definition](https://docs.temporal.io/activity-definition), accessed 2026-11-23)

4. **Effects and replay.** Activity results are written to Event History and "aren't executed again during replay." Workflow code is re-run from the beginning against history; `workflow.SideEffect` executes a short non-deterministic snippet once, records the result as a marker, and returns the recorded value on replay. It comes with a warning: "Do not ever have a Side Effect that could fail, because failure could result in the Side Effect function executing more than once." Code that performs an external effect outside an Activity/SideEffect is a determinism bug, not a supported path. ([event history](https://docs.temporal.io/workflow-execution/event#side-effect), [SideEffect API](https://pkg.go.dev/go.temporal.io/sdk/workflow#hdr-SideEffect_API), accessed 2026-11-23)

5. **Human approval.** A Signal handler sets a flag and the Workflow blocks on `workflow.wait_condition(...)`; the approval is delivered by `handle.signal(...)` and recorded as `WorkflowExecutionSignaled`. Updates provide a synchronous request/response variant with validators and Update IDs. Temporal's own async-completion guidance contrasts a week-long Activity timeout with the signal pattern, recommending a short Activity that notifies the human, completes, and lets the human Signal the workflow later. ([sending messages](https://docs.temporal.io/sending-messages), [activity execution](https://docs.temporal.io/activity-execution), accessed 2026-11-23)

6. **External events.** Signals (client, CLI, or another workflow), Queries, Updates, and Signal-With-Start. Update IDs and `workflow.current_update_info` are the documented dedupe hook for exactly-once message processing. ([sending messages](https://docs.temporal.io/sending-messages), accessed 2026-11-23)

7. **Per-step record.** Event History is an append-only log of the full execution: Activity scheduled/started/completed/failed/timed-out, timers, signals, updates, and workflow-task failures. `ActivityTaskStarted` only appears when the attempt closes, so a pending attempt's count comes from Describe. Operators see history, pending activities, workers, relationships, stack-trace query, and payloads (encoded unless a codec is available). ([event history](https://docs.temporal.io/workflow-execution/event), [CLI](https://docs.temporal.io/cli/command-reference/workflow), [web UI](https://docs.temporal.io/web-ui), accessed 2026-11-23)

### DBOS

1. **Signature and payloads.** "You can turn any Python function into a step" with `@DBOS.step()`; workflows use `@DBOS.workflow()`, transactional work `@DBOS.transaction()`. The only requirement is that outputs be serializable. Python defaults to pickle + Base64, with a custom serializer available; the system database records the serialization format per workflow/step (`py_pickle`, `portable_json`, `java_jackson`). TypeScript exposes `inputSchema.parse` and a `serialization: "portable" | "native"` option. ([step tutorial](https://docs.dbos.dev/python/tutorials/step-tutorial), [system tables](https://docs.dbos.dev/explanations/system-tables), [TS reference](https://docs.dbos.dev/typescript/reference/workflows-steps), accessed 2026-11-23)

2. **Invocation.** An embedded library: "There's no separate orchestration server and no infrastructure required besides Postgres." Steps are ordinary in-process calls; each step writes one checkpoint row. Distribution is multiple app servers sharing the system database and polling durable queues. ([architecture](https://docs.dbos.dev/architecture), accessed 2026-11-23)

3. **Crash detection, retries, idempotency.** Single-node recovery scans for `PENDING` workflows at startup; distributed recovery needs Conductor, which detects a failed executor through the closed websocket and, after a grace period, recovers its workflows elsewhere. Steps have `retries_allowed`, `max_attempts`, `interval_seconds`, `backoff_rate`, `should_retry`, and async `timeout_seconds`. The workflow body must be deterministic; "steps should be idempotent"; once a step completes and is checkpointed it is never re-executed. Database writes are the exception: committing the application write and the checkpoint in one transaction gives exactly-once database effects. ([architecture](https://docs.dbos.dev/architecture), [step tutorial](https://docs.dbos.dev/python/tutorials/step-tutorial), accessed 2026-11-23)

4. **Effects and replay.** `dbos.operation_outputs` holds one row per step (`function_id`, `function_name`, `output`, `error`, start/end timestamps); `DBOS.sleep`, `DBOS.send`, and child-workflow starts are recorded there too. Recovery re-executes the workflow from its checkpointed inputs, returns recorded outputs before each step, and resumes at the first step with no checkpoint. A crash after an external effect but before the checkpoint re-runs that step; the docs say to use an idempotency key at the external provider. ([architecture](https://docs.dbos.dev/architecture), [system tables](https://docs.dbos.dev/explanations/system-tables), [durable execution](https://www.dbos.dev/durable-execution), accessed 2026-11-23)

5. **Human approval.** `DBOS.recv(topic, timeout_seconds=...)` suspends a workflow; `DBOS.send(workflow_id, message, topic, idempotency_key=...)` resumes it. Both messages and the receive deadline persist in Postgres, so a crash during the wait resumes with the original deadline. ([durable execution](https://www.dbos.dev/durable-execution), [workflow communication](https://docs.dbos.dev/python/tutorials/workflow-communication), accessed 2026-11-23)

6. **External events.** Messages land in `dbos.notifications`; `dbos.send_message(..., message_id)` sends "only once no matter how many times" it is called with that ID. `DBOS.get_event` waits on a published key/value and persists the value into the workflow. Workflow-ID-based `SetWorkflowID` and queue `deduplication_id` dedupe starts. ([system tables](https://docs.dbos.dev/explanations/system-tables), accessed 2026-11-23)

7. **Per-step record.** `workflow_status` (status incl. `PENDING/SUCCESS/ERROR/MAX_RECOVERY_ATTEMPTS_EXCEEDED`, `recovery_attempts`, `executor_id`), `workflow_input`, `workflow_output`, `operation_outputs`, `notifications`, `workflow_events(_history)`. The open-source answer to an operator UI is SQL/psql; Conductor adds dashboards and restart-from-step. ([system tables](https://docs.dbos.dev/explanations/system-tables), [architecture](https://docs.dbos.dev/architecture), accessed 2026-11-23)

### Restate

1. **Signature and payloads.** A handler is `(ctx, request) -> response`, typed in the language and registered as a Basic Service, Virtual Object, or Workflow. Python: `@service.handler()` on `async def handler(ctx: Context, req: Request) -> Response`; Go: a method on a struct taking `restate.Context`. The SDK serializes journal entries with JSON by default; `restate-sdk[serde]` supports Pydantic/msgspec/dataclass type hints, and a custom `Serde` is passed as `input_serde=`/`output_serde=`. ([services](https://docs.restate.dev/foundations/services), [serialization](https://docs.restate.dev/develop/python/serialization), accessed 2026-11-23)

2. **Invocation.** Services run "in your infrastructure as containers, serverless functions, VMs, or Kubernetes pods"; the Restate Server "sits in front of your services, similar to a reverse proxy or message broker." Deployments are registered over HTTP (`restate deployments register http://my-service:9080`); handlers are invoked at the ingress path and journal entries stream to the server. ([key concepts](https://docs.restate.dev/foundations/key-concepts), [services](https://docs.restate.dev/foundations/services), accessed 2026-11-23)

3. **Crash detection, retries, idempotency.** An invocation is "tracked … through completion, ensuring it runs exactly once regardless of failures." Service crashes/restarts retry on new instances; if the service cannot ship journal entries, it stops the handler and the server retries elsewhere. Default retry: initial 50 ms, factor 2.0, max 70 attempts, max interval 60 s, action on exhaustion `pause` (manual resume); `kill` returns a terminal error instead. There is no heartbeat; an inactivity timeout (default 1 minute) bounds waiting for new journal entries, with a 10-minute abort timeout. Ingress idempotency keys dedupe retries and return the original result; retention defaults to 24 hours. ([key concepts](https://docs.restate.dev/foundations/key-concepts), [configuration](https://docs.restate.dev/services/configuration), accessed 2026-11-23)

4. **Effects and replay.** `ctx.run` / `restate.Run` wraps a non-deterministic operation and journals "both the operation and its result"; replay skips completed entries. Operations not wrapped in `run` re-execute on retry and are described as breaking deterministic recovery. The journal retains inputs, outputs, and state values, inspectable with `restate invocations journal <id> --payload`. ([durable steps](https://docs.restate.dev/develop/ts/durable-steps), [key concepts](https://docs.restate.dev/foundations/key-concepts), accessed 2026-11-23)

5. **Human approval.** Awakeables are "a durable promise or future that can be recovered after a crash": the handler creates an ID and suspends on it; a human or external system resolves or rejects it through the SDK or the HTTP API (`/restate/awakeables/{id}/resolve`). Named signals deliver repeated values; workflow promises resolve once and are readable many times. The docs frame approvals as a pause/resume pattern, with `restate.select` racing the approval against a sleep timeout. ([external events](https://docs.restate.dev/develop/ts/external-events), [HITL pattern](https://docs.restate.dev/ai/patterns/human-in-the-loop), accessed 2026-11-23)

6. **External events.** Awakeables (one-shot, task-token-like), named signals addressed to an invocation, and workflow promises resolved by shared handlers. Ingress assigns or accepts an `Idempotency-Key` and collapses retries of the same in-flight request. ([actions](https://docs.restate.dev/foundations/actions), [configuration](https://docs.restate.dev/services/configuration), accessed 2026-11-23)

7. **Per-step record.** Introspection tables include `sys_invocation`, `sys_journal`, `sys_journal_events`, `sys_inbox`, `sys_locks`, `sys_promise`, and `state`. `restate invocations describe` shows retry count, last failure, trace ID, and caller; `journal` dumps entries; the UI shows a live execution timeline with retries and nested calls. ([introspection](https://docs.restate.dev/operate/introspection), [managing invocations](https://docs.restate.dev/services/invocation/managing-invocations), accessed 2026-11-23)

### Inngest

1. **Signature and payloads.** `inngest.createFunction(config, trigger, handler)`; the handler receives one object `{event, events, step, runId, logger, attempt}`. `EventSchemas`/`eventType()` with a zod schema gives typed `event.data`; step outputs are JSON values stored server-side. ([create function](https://www.inngest.com/docs/reference/functions/create), [primitives](https://www.inngest.com/docs/durable-execution/primitives), accessed 2026-11-23)

2. **Invocation.** The function is your code, served over HTTP. In standard orchestration "each step … is executed as a separate HTTP request": Inngest calls the endpoint, the SDK runs to a step boundary, posts the result, and Inngest decides what to resume. TypeScript v4 checkpointing runs steps back-to-back in one handler and falls back to standard orchestration on retry or parallel steps; Python always uses standard orchestration. ([how functions are executed](https://www.inngest.com/docs/learn/how-functions-are-executed), [durable workflows](https://www.inngest.com/docs/durable-execution/durable-workflows), accessed 2026-11-23)

3. **Crash detection, retries, idempotency.** `retries` defaults to four retries after the initial attempt; each `step.run` has its own counter; `NonRetriableError` skips retries and `RetryAfterError` sets the next delay. There is no heartbeat: a missing/failed HTTP step result is the failure signal. The docs warn that "a failed attempt can still have changed an external system before it threw or timed out" and recommend idempotency keys/upserts. Function-level `idempotency` and event `id` dedupe for 24 hours. ([retries](https://www.inngest.com/docs/durable-execution/guides-and-advanced/error-handling/retries), [idempotency](https://www.inngest.com/docs/durable-execution/guides-and-advanced/idempotency), accessed 2026-11-23)

4. **Effects and replay.** Completed step results go to a managed state store keyed by a hash of the step ID plus the step index. On resume "Inngest … replay[s] your handler and return[s] saved step results"; completed callbacks do not run again. "Code outside a step can run again each time the handler replays." A duplicate write before the result reached Inngest cannot be undone. ([durable workflows](https://www.inngest.com/docs/durable-execution/durable-workflows), [how functions are executed](https://www.inngest.com/docs/learn/how-functions-are-executed), accessed 2026-11-23)

5. **Human approval.** `step.waitForEvent(id, {event, timeout, match|if})` pauses without keeping compute alive and returns the event or `null` on timeout; `match`/CEL `if` correlate the event to the run. The docs use this for approval flows and note it only sees events sent after it starts listening. ([waitForEvent reference](https://www.inngest.com/docs/reference/typescript/functions/step-wait-for-event), accessed 2026-11-23)

6. **External events.** `inngest.send()`; a sent event `id` is a 24-hour idempotency key. Trigger filters and wait correlations use CEL (`event.data.orderId == async.data.orderId`). ([idempotency](https://www.inngest.com/docs/durable-execution/guides-and-advanced/idempotency), [durable workflows](https://www.inngest.com/docs/durable-execution/durable-workflows), accessed 2026-11-23)

7. **Per-step record.** The Runs view shows status, trigger/run IDs, event payload, a step timeline, each retry's error/timing, and per-step input/output/error tabs with an `Attempt N` badge and "Rerun from step." Insights exposes SQL over `events`, `runs`, `steps`, `step_attempts` (`status`, `output`, `error`, `attempt`). ([inspect runs](https://www.inngest.com/docs/platform-and-operations/inspect-events-and-runs), [insights](https://www.inngest.com/docs/platform/monitor/insights), accessed 2026-11-23)

### AWS Step Functions

1. **Signature and payloads.** A `Task` state names a `Resource`; JSONata mode adds `Arguments`, `Output`, `Assign`, and the reserved `$states` object, while JSONPath mode uses `Parameters`, `ResultPath`, `InputPath`, and `.$`-suffixed fields such as `TimeoutSecondsPath`. There is no compile-time type checking; JSONata type errors fail the state at runtime. ([task state](https://docs.aws.amazon.com/step-functions/latest/dg/state-task.html), [transforming data](https://docs.aws.amazon.com/step-functions/latest/dg/transforming-data.html), accessed 2026-11-23)

2. **Invocation.** The service calls a Lambda function, one of 200+ AWS service integrations, an HTTPS endpoint, or an Activity worker that polls `GetActivityTask` and receives "a string of JSON input for the task) and a taskToken." Orchestration is remote; step code runs in the target service or your worker. ([activities](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-activities.html), accessed 2026-11-23)

3. **Crash detection, retries, idempotency.** `Retry` uses `ErrorEquals`, `IntervalSeconds` (default 1), `MaxAttempts` (default 3), `BackoffRate` (default 2.0), `MaxDelaySeconds`, and `JitterStrategy`; `Catch` routes failures. `TimeoutSeconds` and `HeartbeatSeconds` bound a task, and `SendTaskHeartbeat` resets the clock. "Retries are treated as state transitions" and billed. The cited error-handling pages document no idempotency mechanism; a retry re-invokes the resource. ([error handling](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html), accessed 2026-11-23)

4. **Effects and replay.** The execution history records state entry/exit, input/output, task token, and timeouts. There is no code replay: a retry or Redrive re-invokes the resource, and arbitrary side effects are not recorded. ([execution details](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-view-execution-details.html), [GetExecutionHistory](https://docs.aws.amazon.com/step-functions/latest/apireference/API_GetExecutionHistory.html), accessed 2026-11-23)

5. **Human approval.** The callback pattern passes `$$.Task.Token` to an external worker (`sendMessage.waitForTaskToken`), which later calls `SendTaskSuccess`/`SendTaskFailure` (`error` ≤ 256 chars, `cause` ≤ 32,768). Standard workflows can pause up to one year; Express supports only request/response integrations. Heartbeats are recommended to avoid waiting indefinitely. ([connect to a resource](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html), accessed 2026-11-23)

6. **External events.** A running task resumes only through the token APIs; the token is single-task and same-account. After timeout the token is invalidated and calls fail with `TaskTimedOut`. No dedupe is documented on the cited pages. ([connect to a resource](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html), [activities](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-activities.html), accessed 2026-11-23)

7. **Per-step record.** Console Graph/Table/Events views; Standard histories are kept 90 days and include input/output with `truncated` flags; `aws stepfunctions get-execution-history --includeExecutionData` pages through them. Express histories require CloudWatch Logs (levels `OFF`/`ERROR`/`FATAL`/`ALL`, best-effort). ([execution details](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-view-execution-details.html), [CloudWatch logs](https://docs.aws.amazon.com/step-functions/latest/dg/cw-logs.html), accessed 2026-11-23)

### Argo Workflows

1. **Signature and payloads.** Templates declare `inputs.parameters` (`name`, `value`, optional `description`, `enum`) and `inputs.artifacts`; callers pass `arguments.parameters` and artifact references such as `{{tasks.step-A.outputs.artifacts.output-artifact-1}}`. Values are interpolated as strings with expression functions (`asInt`, `jsonpath`, `toJson`, Sprig); outputs are parameters read from a file path or artifacts. There is no schema or type validation. ([workflow inputs](https://argo-workflows.readthedocs.io/en/latest/workflow-inputs), accessed 2026-11-23)

2. **Invocation.** Container, script, HTTP, and executor-plugin templates run as Kubernetes Pods; the Argo controller reconciles the Workflow and Kubernetes schedules the pods. `argo logs WORKFLOW POD` reads pod logs. ([templates](https://argo-workflows.readthedocs.io/en/latest/workflow-templates), [argo logs](https://argo-workflows.readthedocs.io/en/latest/cli/argo_logs), accessed 2026-11-23)

3. **Crash detection, retries, idempotency.** Template-level `retryStrategy` has `limit`, `retryPolicy` (`Always`/`OnFailure`/`OnError`/`OnTransientError`; `OnFailure` is the default except with an expression on 3.5+), an `expression` over `lastRetry.exitCode/status/duration/message`, and backoff configuration. No heartbeat field is documented; pod phase and exit code are the signals. ([retries](https://argo-workflows.readthedocs.io/en/stable/retries), accessed 2026-11-23)

4. **Effects and replay.** Opt-in `memoize` stores template outputs in a ConfigMap (`workflows.argoproj.io/configmap-type: Cache`, entry cap 1,048,576 characters) and exposes `memoizationStatus`. The docs say it was designed for pure steps and "workflows won't enforce this on you." Otherwise a retried or resubmitted pod re-executes; large data lives in artifacts. There is no replay. ([memoization](https://argo-workflows.readthedocs.io/en/latest/memoization), accessed 2026-11-23)

5. **Human approval.** A `suspend: {}` template stops scheduling new steps until `argo resume WORKFLOW`; an optional `suspend.duration` resumes automatically. Intermediate Parameters let a suspended node's `inputs.parameters` (with `enum`) be supplied by a human, with `outputs.parameters` using `valueFrom.supplied: {}`. No maximum wait is documented. ([suspending](https://argo-workflows.readthedocs.io/en/latest/walk-through/suspending), [intermediate inputs](https://argo-workflows.readthedocs.io/en/latest/intermediate-inputs), accessed 2026-11-23)

6. **External events.** The built-in `/api/v1/events/{namespace}/{discriminator}` endpoint plus a `WorkflowEventBinding` selector can submit a workflow; `argo events` notes "Events may not always be processed in order" and returns 503 when its queue is full. Argo Events chains EventSource → EventBus → Sensor → `argoWorkflow` operation (`submit`, `resume`, `retry`, `suspend`, …). No dedupe/idempotency is documented. ([events](https://argo-workflows.readthedocs.io/en/stable/events), [Argo Events trigger](https://argoproj.github.io/argo-events/sensors/triggers/argo-workflow), accessed 2026-11-23)

7. **Per-step record.** `Workflow.status.nodes` carries `phase`, human-readable `message`, `nodeFlag` (hooked/retried), `inputs`, and `memoizationStatus`; `argo get` prints Status/Conditions/Progress and a STEP/TEMPLATE/PODNAME/DURATION/MESSAGE table; `argo logs` follows pod logs; the UI shows pod, host node, phase, and per-template I/O. ([fields](https://argo-workflows.readthedocs.io/en/latest/fields/), [argo get](https://argo-workflows.readthedocs.io/en/latest/cli/argo_get), accessed 2026-11-23)

### Dagster

1. **Signature and payloads.** `@dg.op` wraps a compute function whose inputs are ordinary arguments, typed with `In(dagster_type=...)` or return annotations; tuple annotations map to multiple `Out`s. Dagster types are validated at runtime, not a wire schema. Outputs are persisted by IO managers (`handle_output`/`load_input`, `Out(io_manager_key=...)`); op config is a pydantic `Config` subclass. ([ops](https://dagster.io/docs/guides/build/ops), [IO managers](https://dagster.io/docs/api/dagster/io-managers), accessed 2026-11-23)

2. **Invocation.** The job's executor decides: the default `multi_or_in_process_executor` runs each step in its own process, `in_process_executor` runs in-process, and integrations run steps as Celery tasks, Docker containers, ephemeral Kubernetes pods, or ECS tasks. The daemon and webserver are separate from the run worker that executes op code. ([run executors](https://dagster.io/docs/guides/operate/run-executors), accessed 2026-11-23)

3. **Crash detection, retries, idempotency.** Per-op `RetryPolicy(max_retries=...)` or `RetryRequested`; run-level retries via `dagster/max_retries` + `dagster/retry_strategy: "ALL_STEPS"` or daemon `run_retries`. Run monitoring (`max_runtime_seconds`) detects hanging runs and restarts crashed run workers. Sensors dedupe with `run_key`; the docs state no general idempotency guarantee. ([op retries](https://dagster.io/docs/guides/build/ops/op-retries), [run retries](https://dagster.io/docs/deployment/execution/run-retries), [run monitoring](https://dagster.io/docs/deployment/execution/run-monitoring), accessed 2026-11-23)

4. **Effects and replay.** Ops emit a stream of structured events — `AssetMaterialization`, `ExpectationResult`, `Output` — and IO managers store outputs for downstream loading. A retry re-executes the op's compute function; `ALL_STEPS` re-runs every step, otherwise execution resumes at the failure. Arbitrary side effects are captured only if the author emits an event; there is no replay. ([ops](https://dagster.io/docs/guides/build/ops), [run retries](https://dagster.io/docs/deployment/execution/run-retries), accessed 2026-11-23)

5. **Human approval.** No first-class pause/resume or approval operator was found in the open-source docs. The documented gating pattern is a sensor that emits a `RunRequest` only when an external approval condition exists. ([sensors](https://dagster.io/docs/guides/automate/sensors), accessed 2026-11-23)

6. **External events.** `@dg.sensor(job=..., minimum_interval_seconds=5)` polls and yields `RunRequest(run_key=...)` or `SkipReason`; schedules and Declarative Automation (asset-condition rules) are the other entry paths. Push delivery is not part of this model. ([sensors](https://dagster.io/docs/guides/automate/sensors), [declarative automation](https://dagster.io/docs/guides/automate/declarative-automation), accessed 2026-11-23)

7. **Per-step record.** Per-step events and logs (`context.log.info`) appear on the run details page; the event stream is visualized in the UI. CLI: `dagster run`, `dagster job`, `dagster-daemon run`. ([ops](https://dagster.io/docs/guides/build/ops), [CLI](https://dagster.io/docs/api/clis/cli), accessed 2026-11-23)

1. **Signature and payloads.** `@flow` and `@task`; Python generic type variables preserve input/output types. ([tasks API](https://www.prefect.io/docs/v3/api-ref/python/prefect-tasks), last modified 2026-11-19)

([interactive workflows](https://www.prefect.io/docs/v3/advanced/interactive), [states](https://www.prefect.io/docs/v3/concepts/states), accessed 2026-11-23)

([automations](https://www.prefect.io/docs/v3/concepts/automations), [events](https://www.prefect.io/docs/v3/concepts/events), accessed 2026-11-23)

7. **Per-step record.** Per-run/task state (including `AwaitingRetry`, `Running`, `Crashed`, `Paused`), logs (with `log_prints`), persisted results retrievable later, and a UI state-transition table that explains transitions such as `Running → Failed` as a code exception. ([states](https://www.prefect.io/docs/v3/concepts/states), accessed 2026-11-23)

([tasks](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/tasks.html), accessed 2026-11-23)

([how it works](https://trigger.dev/docs/how-it-works), [self-hosting](https://trigger.dev/docs/self-hosting/overview), accessed 2026-11-23)

3. **Crash detection, retries, idempotency.** "A task is retried if an error is thrown. By default, we retry 3 times"; `maxDuration` and `ttl` are configurable. Idempotency keys dedupe triggers, but "it does not make the code inside a task's run() function idempotent." ([tasks overview](https://trigger.dev/docs/tasks/overview), [idempotency](https://trigger.dev/docs/idempotency), accessed 2026-11-23)

4. **Effects and replay.** Only failed subtasks and their successors retry, with completed subtask output "cached based on its idempotency key"; code outside subtasks re-runs on each attempt; `ctx.run.isReplay` reports replay. ([how it works](https://trigger.dev/docs/how-it-works), [replaying](https://trigger.dev/docs/replaying), accessed 2026-11-23)

5. **Human approval.** Waitpoint tokens: `wait.createToken({timeout, idempotencyKey})`, `await wait.forToken<ApprovalToken>(tokenId)`, and `wait.completeToken(tokenId, {status: "approved"})` from the SDK or an HTTP POST. Waiting runs consume no compute; AI tool approvals use `addToolApprovalResponse`. ([wait for token](https://trigger.dev/docs/wait-for-token), accessed 2026-11-23)

6. **External events.** Delivery to a waiting run is token completion (SDK or HTTP); starting runs uses `tasks.trigger` with an optional `idempotencyKey`. No generic event bus into a running run is documented. ([wait for token](https://trigger.dev/docs/wait-for-token), [tasks API](https://trigger.dev/docs/management/tasks/trigger), accessed 2026-11-23)

7. **Per-step record.** `runs.retrieve("run_1234")` returns payload, output, and `attempts` with `attempt.error`; `runs.list`, `runs.replay`, and `runs.subscribeToRun` exist; the dashboard shows run traces. ([retrieve run](https://trigger.dev/docs/management/runs/retrieve), [replay run](https://trigger.dev/docs/management/runs/replay), accessed 2026-11-23)

### Hatchet

1. **Signature and payloads.** TypeScript `hatchet.task({name, retries, fn: async (input, ctx) => …})` and `hatchet.durableTask({..., executionTimeout})`; Python `@hatchet.task(name=..., input_validator=UpstreamInput, retries=5)` validates the payload against the validator. ([retry policies](https://docs.hatchet.run/v1/retry-policies), [durable event waits](https://docs.hatchet.run/v1/durable-event-waits), accessed 2026-11-23)

2. **Invocation.** User code runs in your worker processes (`hatchet.worker("dag-worker", workflows=[...]); worker.start()`), with per-worker `slots`; the Go server schedules and dispatches over gRPC. ([workers](https://docs.hatchet.run/v1/workers), accessed 2026-11-23)

3. **Crash detection, retries, idempotency.** `retries`, exponential backoff (`maxSeconds`, `factor`), `RetryAfterError`, `NonRetryableError`, `ctx.retryCount()`; crash detection is heartbeat-based. The docs advise ensuring operations are idempotent before enabling retries. ([retry policies](https://docs.hatchet.run/v1/retry-policies), [workers](https://docs.hatchet.run/v1/workers), accessed 2026-11-23)

4. **Effects and replay.** Durable tasks journal their waits: "When it resumes, it reads the event from the durable event log and continues." What is checkpointed at each non-wait step boundary is not documented on the reviewed pages; non-durable tasks re-run wholesale per retry. ([durable event waits](https://docs.hatchet.run/v1/durable-event-waits), accessed 2026-11-23)

5. **Human approval.** `ctx.waitForEvent(EVENT_KEY)` (TS) / `ctx.aio_wait_for_event` (Py) with CEL filters, a scope, and lookback windows; the DAG docs call event waits "a natural fit for human-in-the-loop workflows" with a deadline, but there is no dedicated approval API. ([durable event waits](https://docs.hatchet.run/v1/durable-event-waits), [DAGs](https://docs.hatchet.run/v1/directed-acyclic-graphs), accessed 2026-11-23)

6. **External events.** `hatchet.event.push(key, payload, scope=...)` from the SDK or an incoming webhook; the pushed key must match the wait. Dedupe is not documented. ([durable event waits](https://docs.hatchet.run/v1/durable-event-waits), accessed 2026-11-23)

7. **Per-step record.** Dashboard traces preserve input/output and logs, with full-text log search and OpenTelemetry; no per-step CLI inspection command is documented. ([observability](https://hatchet.run/platform/observability), [logging](https://docs.hatchet.run/v1/logging), accessed 2026-11-23)

### AWS Lambda durable functions

1. **Signature and payloads.** The handler is wrapped by `withDurableExecution` and receives `(event, context: DurableContext)`; Go receives `durable.Context` and calls `durable.Step[T](ctx, name, func(StepContext) (T, error))`. Results are JSON by default through a configurable `Serdes`; a serializer failure fails the step without retry. ([key concepts](https://docs.aws.amazon.com/durable-execution/getting-started/key-concepts/), [step reference](https://docs.aws.amazon.com/durable-execution/sdk-reference/operations/step/), accessed 2026-11-23)

2. **Invocation.** The handler runs in Lambda. The SDK calls the Lambda checkpoint API after each operation; a suspension ends the invocation and the service re-invokes the function, which replays the checkpoint log. The invocation timeout is at most 15 minutes; the durable execution timeout is at most one year. ([key concepts](https://docs.aws.amazon.com/durable-execution/getting-started/key-concepts/), accessed 2026-11-23)

3. **Crash detection, retries, idempotency.** Step retry strategies default to 6 attempts, 5 s first delay doubling to 60 s, full jitter. `StepSemantics.AtLeastOncePerRetry` (default) re-executes a step whose outcome was not checkpointed; `AtMostOncePerRetry` "never re-executes an interrupted attempt" and surfaces `StepInterruptedError`. The SDK enforces determinism by matching operation names/types against the checkpoint log; a mismatch is a non-deterministic execution error. ([step reference](https://docs.aws.amazon.com/durable-execution/sdk-reference/operations/step/), [idempotency](https://docs.aws.amazon.com/durable-execution/patterns/best-practices/idempotency/), accessed 2026-11-23)

4. **Effects and replay.** A checkpoint is "a saved record of a completed durable operation: its type, name, inputs, result, and timestamp." On resume the handler runs from the beginning; completed operations return stored results; the first operation without a checkpoint executes. Code outside steps re-runs and is flagged as non-deterministic if it reads time/random/external state. ([key concepts](https://docs.aws.amazon.com/durable-execution/getting-started/key-concepts/), accessed 2026-11-23)

5. **Human approval.** `createCallback` returns a callback ID and a future; `waitForCallback` combines creation, submission, and waiting. The external system calls `SendDurableExecutionCallbackSuccess`/`Failure`; the backend starts a new invocation. `timeout` and `heartbeatTimeout` bound the wait, and the docs insist on setting a timeout. ([callback reference](https://docs.aws.amazon.com/durable-execution/sdk-reference/operations/callback/), [pause and resume](https://docs.aws.amazon.com/durable-execution/patterns/best-practices/pause-resume/), accessed 2026-11-23)

6. **External events.** Callback completion is the delivery path; the callback ID goes to the external system, which posts the result back through the Lambda API. No generic event bus into a running execution is documented. ([callback reference](https://docs.aws.amazon.com/durable-execution/sdk-reference/operations/callback/), accessed 2026-11-23)

7. **Per-step record.** The checkpoint log and operation history record type, name, inputs, result, and timestamp per operation; CloudWatch logs and the durable-execution telemetry/MCP exporter are the operator surfaces. ([key concepts](https://docs.aws.amazon.com/durable-execution/getting-started/key-concepts/), [guide home](https://docs.aws.amazon.com/durable-execution/), accessed 2026-11-23)

## Borrow / avoid for Factory

### 1. Handler signature and typed payloads

**Borrow**
- **One object argument, not many.** Temporal's docs recommend a single object parameter so fields can be added without changing the signature; several SDKs' type-safe start calls and the UI accept only one argument. Factory's generated state sum type is that object; keep it additive.
- **A separate context/envelope argument.** Restate passes `Context` beside the request; DBOS exposes execution metadata on the decorated function's context. Factory should pass `(activationEnvelope, state)` — metadata must not be smuggled into workflow state, or state evolution breaks whenever the harness adds a field.
- **Explicit serialization and a schema at the boundary.** Restate's `Serde`, DBOS's `serialization` column, and AWS durable's per-step `Serdes` all make the wire format an explicit, recorded choice. Factory's compile step should generate the state codec and record the schema/definition digest with each activation, not rely on language-native defaults silently.

**Avoid**
- **Multi-parameter handlers** (Temporal warns they break type-safe clients and the Web UI and make additive changes harder).
- **Untyped string templates as the type system** (Argo's `{{inputs.parameters.x}}`, Step Functions' JSONPath). Both work, but neither gives the compile-time guarantee Factory's owner asked for.
- **Implicit payload channels with size limits as the state store** (Airflow XComs are metadata-DB values "only designed for small amounts of data"; DBOS explicitly warns that checkpoint size equals output size). Factory should pass artifact/workdir references and digests, never blobs.

### 2. Step invocation and code location

**Borrow**
- **The orchestrator never executes user code.** Temporal workers, DBOS's embedded library, Restate services behind the server, and Inngest endpoints all separate scheduling/state from execution. Factory's daemon/VM split is the same shape; keep the contract narrow and versioned.
- **One activation, one unit of work.** AWS durable and Cloudflare make suspension end the invocation and resume later; the handler is not kept alive for a wait. Factory's re-entrant handler should do the same: perform the state's work, return the next state, exit.
- **Daemon owns the worktree and the store.** No surveyed engine lets the orchestrator share a transaction with the worker's filesystem. Factory should keep the worktree snapshot and the state write on the daemon side, as decided.

**Avoid**
- **One engine round-trip per micro-step.** Step Functions, Argo, Airflow, and Prefect serialize each step's I/O through the orchestrator. That is appropriate for short deterministic tasks, not for a handler that runs tests, spawns agents, and performs direct effects for minutes.
- **Holding a process or worker slot during a human wait.** Prefect's `pause_flow_run` is explicitly distinguished from `suspend_flow_run`, which "exits the flow and tears down infrastructure"; Airflow 3.3+ holds no worker slot in `awaiting_input`; Temporal's async-completion guidance warns about a week-long Activity timeout. Factory must persist the wait and release the activation.
- **Long-lived SSH/RPC sessions as the activation channel.** Restate's "if the service cannot send journal entries, stop the handler" and DBOS's executor-heartbeat model both assume a supervisory connection. Factory should make the activation a bounded request with an explicit lease, not an open-ended stream.

### 3. Crash detection, retries, idempotency

**Borrow**
- **Explicit liveness contract.** Temporal's Start-To-Close + Heartbeat timeouts, Step Functions' `HeartbeatSeconds`, AWS durable's callback heartbeat, and Hatchet's worker heartbeat all detect a dead executor by absence of a signal. Factory's activation envelope should carry a lease/heartbeat, a deadline, and a typed `Crashed` outcome.
- **Typed non-retryable failures.** Temporal's `non_retryable` `ApplicationError`, Restate's `TerminalError`, Inngest's `NonRetriableError`, Cloudflare's `NonRetryableError`, and Hatchet's `NonRetryableError` all let the handler declare "do not retry this." Factory's state result should have the same distinction rather than inferring retryability from an error string.
- **Bounded, declared retry policy.** Step Functions' `MaxAttempts` default 3, Inngest's 4 retries, DBOS's `max_attempts`, Argo's `limit`, and Prefect's `retries` all bound retries explicitly. Factory should put the bound in the program or project config and record the attempt number in the envelope.
- **Per-effect at-least-once vs at-most-once.** AWS durable's `StepSemantics` is the clearest precedent: default at-least-once for idempotent work, at-most-once per retry for side-effecting work, with an `Interrupted` error when the outcome is unknown. Factory's mediated library should require the same declaration per operation (push, PR create/update, merge, tracker transition, agent dispatch).

**Avoid**
- **Unlimited default retries.** Temporal's Activity default is unlimited attempts; that is acceptable only because activities are meant to be idempotent. Factory should not inherit it for direct effects.
- **Retrying the whole workflow.** Temporal's docs explicitly discourage it: replay repeats the same logic without resolving the cause. Factory should retry the state or route to a failure state, never rewind to intake.
- **Promising exactly-once.** Only DBOS gets exactly-once database effects by committing the app write and the checkpoint in one transaction. Everything else is at-least-once plus idempotency; Factory's daemon DB and VM worktree cannot share a transaction, so the honest claim is at-least-once activation delivery with idempotent mediated operations and reconciliation.

### 4. Direct side effects, journaling, replay

**Borrow**
- **A declared boundary and an explicit warning that everything outside it re-runs.** Inngest says "code outside a step can run again"; Temporal requires determinism outside Activities; DBOS requires a deterministic workflow body; AWS durable flags non-deterministic code outside steps. Factory's boundary is the activation: effects inside it are direct and never replayed, so the state returned is the only durable progress.
- **Journal the effect when the effect must be replay-safe.** Temporal's `SideEffect` and Restate's `ctx.run` both record an operation and its result. Factory can use the same idea for *audit*: the activation envelope records each mediated effect with its idempotency key and result, without pretending the handler can be replayed.
- **Make the state transition, not the handler, authoritative.** DBOS's checkpoint is written after the step; Restate journals state updates alongside execution. Factory should write the new state and the envelope atomically in the daemon, and treat any handler-local mutation as lost.

**Avoid**
- **Selling an event log as replay.** Temporal's Event History genuinely replays code; Step Functions' execution history does not, and Argo has no replay at all. Factory's activation envelope is an audit record, and the docs should say so.
- **Mutating a shared durable object from the handler.** Restate's Virtual Object single-writer rule and DBOS's ban on races in the workflow body exist because concurrent mutation destroys the recovery story. Factory's state should be immutable input/output, with the daemon serializing per Task.
- **Relying on a checkpoint to be atomic with an external effect.** DBOS can do it only for DB writes in the same Postgres transaction. In Factory, `git push`/PR/merge/tracker calls are outside the daemon DB; each needs its own idempotency key and a reconcile-before-retry step.

### 5. Human approval

**Borrow**
- **A durable wait with an externally resolvable token.** Restate's awakeable (`resolve`/`reject`, also over HTTP), Step Functions' task token (`SendTaskSuccess`/`Failure`), DBOS's `recv`/`send`, Inngest's `waitForEvent`, and AWS durable's callback all persist the wait and let a separate actor resolve it. Factory's checkpoint should record a checkpoint ID, the asked artifacts, the decision schema, and a deadline; the CLI/API resolves it; the next activation receives the decision in state.
- **A typed decision and a recorded rationale.** Temporal Updates have validators and Update IDs; Restate can reject an awakeable with a terminal error; Step Functions carries `error`/`cause`. Factory should record who decided, what they chose, and why, and validate the decision against the checkpoint's schema.
- **A deadline and an expiry outcome.** DBOS's `recv` returns `None` on timeout, Inngest returns `null`, and AWS durable's callback has `timeout`/`heartbeatTimeout`. Factory's checkpoint needs an explicit expiry edge, not an indefinite `Waiting`.

**Avoid**
- **Indefinite waits.** Step Functions Standard can wait a year, Argo's `suspend` has no documented maximum, and Inngest's wait only sees events after it starts. A Factory Task should not hold a worktree or queue slot indefinitely; expiry should route to a defined state.
- **Approval by replaying the handler.** A Temporal signal is safe because replay is deterministic. Factory must resume with the persisted state and must not re-run the pre-approval effects; the checkpoint record is the resume point, not the handler's code path.

### 6. External events

**Borrow**
- **Push into the waiting record with a correlation key and a dedupe key.** Inngest events carry a 24-hour `id` and wait on a CEL `match`/`if`; DBOS messages have `message_id`; Restate awakeables have an ID; Temporal Update IDs serve the same role. Factory's event intake should key on the provider event ID, store the raw event, evaluate the match/guard, and deliver at most once to a waiting Task.
- **Events can interrupt a waiting state, not just start a workflow.** Temporal Signals and Inngest `waitForEvent` both do this, and the current spec already gives checkpoints event edges (a PR review or base move can interrupt a merge checkpoint). Keep that.
- **A reconciliation poll beside the push path.** Temporal's polling-Activity pattern and DBOS's Postgres polling show that a durable store plus a poller is a legitimate fallback when a provider cannot push. Factory's tracker adapter already polls; use it to recover missed events.

**Avoid**
- **Polling-only sensors that occupy execution capacity.** Airflow sensors and Dagster sensors poll on an interval; Airflow's deferrable operators and Prefect's event-driven automations exist precisely to avoid holding a worker. Factory should keep waiting out of the activation.
- **Assuming ordering or exactly-once delivery.** Argo's docs say events "may not always be processed in order"; Inngest's wait sees only later events; Step Functions tokens expire. Carry sequence/timestamp and make handlers tolerate late and duplicate events.

### 7. Per-step record and operator view

**Borrow**
- **The per-step ledger shape.** Temporal's event history (scheduled/started/completed/failed + attempt + timeouts), DBOS's `operation_outputs` (`function_id`, name, output, error, start/end), and AWS durable's checkpoint (`type`, `name`, `inputs`, `result`, `timestamp`) converge on the same fields. Factory's activation envelope should carry: activation ID, Task ID, state name, definition digest, attempt, workdir reference, start/end, outcome, returned-state reference, effect records (operation, idempotency key, result), log/artifact references, and the triggering event ID.
- **Live introspection of a stuck activation.** Temporal's `__stack_trace` query, Restate's `invocations describe` (retry count, last failure), Argo's `argo get`/`logs`, and Airflow's task-instance detail all answer "what is it doing right now?" Factory's `task inspect` should show the current activation, heartbeat age, last effect, and VM log pointers.
- **A projection over an append-only log.** DBOS's tables and Temporal's history both let an operator rebuild the timeline; Factory's daemon already commits transitions before effects. Keep the envelope append-only and project it for the CLI.

**Avoid**
- **Storing artifacts or logs in the metadata database.** Airflow's XCom is explicitly for small values; DBOS warns that large outputs make large checkpoint writes. Factory should keep artifacts in the worktree/VM and record refs plus digests.
- **Retention surprises.** Step Functions keeps Standard histories 90 days; DBOS retention is a Conductor policy. Factory should declare its retention and keep the audit projection independent of the working VM (which is deleted on idle).
- **A record that only says "failed."** Every surveyed operator view carries at least the failing step, the error, and the attempt; several carry input/output. Factory's envelope should make a failure legible without opening the VM.

## What this implies for the contract, failure-model, and events tickets

- **Contract (#13, #14):** the handler takes `(envelope, state)` and returns `(nextState, outcome)`; mediated operations carry an idempotency key and an explicit at-least-once/at-most-once semantic; the daemon records the effect result, not the handler's intent.
- **Failure model (#15):** an activation lease plus heartbeat and deadline; typed retryable/non-retryable outcomes; bounded attempts; `Crashed` when the lease expires; no replay claim; reconcile-before-retry for git/PR/tracker/agent effects.
- **Events (#16):** a typed event record with provider ID, dedupe key, match/guard, and target (waiting state or new Task); push where available, poll as reconciliation; checkpoint deadlines and expiry edges.
- **State semantics (#12):** state is immutable per activation, returned whole; the daemon writes it with the envelope; a definition digest is pinned per Task, which is Factory's substitute for Temporal's versioning/patching machinery.
