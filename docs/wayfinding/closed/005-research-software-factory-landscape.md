## Question

Broad survey of existing software factories / autonomous agent orgs / agent-harness projects (beyond the four named inspirations): e.g. MetaGPT, ChatDev, AutoGen/AG2 groups, Claude-based swarms, DevRel/Devin-style systems, OpenAI/Anthropic agent orchestration writeups, and any new 2025–2026 entrants. For each, capture: architecture (how deterministic structure meets agent autonomy), how they handle multi-project management and trackers, permission/capability models, the failure modes they hit. Verdict: a comparative table plus the recurring anti-patterns ("spaghetti agents") the industry keeps re-discovering, and the structural ideas Factory should adopt or avoid.

## Resolution

**Scope and reading.** This is a survey of public primary sources available on 2026-10-14. “Not documented” means the source does not establish a capability; it is not a claim that a vendor has none. The four map inspirations (mattpocock/skills, T3 Code, paperclip, pi.dev) are intentionally not re-surveyed here; see the map and ticket 002. Agent frameworks generally do not provide multi-project tracker management out of the box, while commercial and internal coding agents tend to wrap one task/repository with a product-specific lifecycle.

### Recurring anti-patterns (“spaghetti agents”)

1. **Peer swarm without ownership.** Everyone can choose work, mutate shared files, and negotiate. This recreates duplicate effort, lock/coordination races, conflicting conventions, unmerged PRs and occasionally destructive competition. A role prompt or CEO persona alone does not fix this.
2. **LLM decides every transition.** Unbounded chat/speaker selection/plan mutation invites loops, redundant workers, stalled tasks, excessive token spend, or work that never reaches a verifiable terminal state. Add deterministic budgets, state transitions, idempotent claims and explicit completion conditions.
3. **Implicit shared context.** Parent, siblings, tracker, repository, and tools do not magically share current state. Relay structured task contracts and findings with provenance; make durable artifacts/status authoritative. Avoid forwarding entire noisy transcripts or trusting lossy summaries for decisions.
4. **Uncoordinated concurrent writes.** Separate contexts do not imply compatible code. Use independent worktrees/branches and explicit ownership; serialize integration and merge decisions. Parallelize read-only discovery, test generation, review, and genuinely disjoint shards first.
5. **Permission by prompt.** “Do not deploy” is not an authorization boundary. Scope credentials, network, filesystem, project and tracker actions in the runtime; fail closed at tool/operation boundaries, and require human confirmation for irreversible actions. Treat issue text, comments, MCP results, and repo content as untrusted prompt-injection surfaces.
6. **Success = model says done / tests pass.** Tests can be incomplete and agents can game a narrow verifier or silently fall back to tools. Require observable end-state checks (tests, CI, diff, PR state), bounded retries, and human merge/release review.
7. **Build the fleet before proving one loop.** Hundreds of sessions force investment in VM lifecycle, identity propagation, crash recovery, integrations and audit. That infrastructure is real work, not free scalability.

### Structural recommendations for Factory

**Adopt:**

- Make the **workflow state machine authoritative** (issue claimed → triaged/ready → implementation → checks → independent review → PR/merge decision), while agents own bounded judgment-heavy nodes. This combines Stripe blueprints, OpenHands event state, and the strong parts of SOP pipelines without hardcoding every reasoning step.
- Model **project as a first-class boundary**: tracker adapter, repo(s), credentials, execution target, context/rules, and policy all attach to a project. Every run is explicitly bound to one project and issue; cross-project search/delegation is a separate, opt-in capability. Do not let an agent’s broad token silently select its project scope.
- Dispatch through **typed task contracts** (objective, acceptance criteria, inputs/artifact references, allowed tools, write scope, budget/deadline, expected output schema). Persist plans, decisions, events and artifacts; the tracker remains the external work record while Factory’s run log gives replay/debug evidence.
- Start with **one writer per issue/branch**. Use read-only exploration/review and small, independently verifiable parallel slices; integration is a deterministic/owner-controlled boundary. When concurrency is justified, allocate isolated workspaces and serialize merge/PR side effects.
- Add **role capability profiles + action-level checks**: least privilege for tracker and Git operations, allowlisted MCP tools, per-project secrets, network/filesystem isolation, spend/time/worker limits, and approval for merge, deployment, destructive, or secret-bearing operations. Enforcement must sit outside the prompt.
- Make **retry, resume, cancellation, and completion deterministic**. Cap model calls, agent count, retry/CI rounds and wall time; checkpoint transitions and record tool/action outcomes. Evaluate final state and provenance, not exact agent trajectory.
- Use deterministic selectors/sharding for work requiring exhaustive coverage (repository scans, migrations, triage batches), then agents for the interpretation and synthesis that cannot be scripted.

**Avoid:** free-form agents negotiating over shared work; general-purpose coordinator recursion; parallel code writers touching the same tree; treating the tracker’s labels as sufficient authorization; global MCP bundles or inherited credentials; long-lived runners without cancellation/resource bounds; and a giant “universal factory” abstraction before the issue→PR loop works across two projects.

**Bottom line:** Factory’s differentiator should be the reliable multi-project control plane—explicit project identity, tracker adapters, durable workflow state, auditable capability enforcement, and human-governed merge/deploy—not a simulated software company with many agents. Model autonomy belongs inside small, inspectable, replaceable workflow steps.

#### Tessl (tessl.io) — the context-driven counter-thesis

A hosted, **closed-source** platform (proprietary CLI on npm under `tesslio`, `SEE LICENSE.md`, ~55k monthly installs, daily releases; credits pricing, EU region, SSO) whose explicit pitch is "build your software factory, one skill at a time" and whose method whitepaper argues the **opposite of Factory's stated premise**: workflows defined in code are brittle. ([What is Tessl?](https://docs.tessl.io/overview/readme.md) · [Context-driven factories](https://tessl.io/blog/context-driven-factories))

**Components** ([docs overview](https://docs.tessl.io/overview/readme.md)):

- **Registry & package manager**: skills/plugins versioned, installed, rolled back like dependencies; one searchable index across public and private context; agent-agnostic (Claude Code, Cursor, Codex, Gemini, Antigravity, and custom OpenCode/OpenClaw setups are documented).
- **Governance**: skills scored against best practices and company standards with Snyk-powered security scoring; RBAC over who can create/publish/view; install and publish policies; "required skills" enforcement across workspaces; full audit trail.
- **Evals**: measures a skill's real impact by running agents on real tasks with and without the skill; test variants compare models, agents, harnesses, skill revisions. Claims: 94% task success up from 67% (Fastify); 74% of code-review findings are real defects, up from 50%.
- **Observability**: sees where skills actually *activate* across agent sessions; mines agent logs for recurring mistakes → skill fixes (this is the steer-mining loop the map priced in ticket 004).
- **Context & Findings**: connects SCM accounts and scans repositories at organization level for skill drift, overlap, and unmanaged copies.
- **Tessl Agent** (open beta): conversational agent that monitors and improves the agentic setup.

**Method** ("skills → loops → factory", [context-driven factories, 15 Sep 2026](https://tessl.io/blog/context-driven-factories)):

- **Workflow definition lives in context, not code.** "Code is still present, as scripts, CLIs, and MCP tools the agent can call, but it does not sit in the outer loop deciding how the agent progresses through the task." The ticket-to-PR flow is a *set of skills* (`triage-issue` → `pr-shepherd`), not a coded pipeline; the agent reads the process and exercises judgment, handling exceptions (multi-repo features, stacked PRs, light review for copy fixes) without special-case branches.
- **Every workflow and standard lives in a plugin**, checked into your repos, shared across projects via the registry — review learnings feed implementation automatically because both surfaces read the same skill ("review improved generation without anyone wiring the two together").
- **Loops are scheduled skills**: a `schedules` block in `tessl.json` pushed to the default branch turns a plugin into an automation. Executes as Tessl **cloud runs** ("no CI setup"); per-schedule agent selection (`claude` default, `claude-code`, `cursor`, `codex`, `gemini`, `tessl-agent`); secrets via named workspace environments, else a read-only GitHub token. ([Automations](https://docs.tessl.io/automations/overview.md), [Schedules](https://docs.tessl.io/automations/overview/overview.md))
- **Shipped loops** include: automated code review, STRIDE/OWASP security scanning, docs maintenance, model & harness evaluation, agent cost benchmarking, test-and-fix, incident post mortem, model routing ("route routine work to the cheapest model that holds quality").
- **Team legibility is the selling point**: process lives in PR-reviewable skill files anyone can propose changes to; three failure reasons are given for the code-first alternative: workflows in code are brittle and can't improve as models ship; knowledge is siloed so improvements don't flow between workflows; tooling-first builds never earn team buy-in.

**Why it matters for Factory (decision fuel):**

- **Direct challenge to the "code-defined workflows, deterministic state machine" premise** (map Notes §3, tickets 006/008): Tessl claims field evidence that the coded-pipeline build fails — "the pipeline hardens around whatever the models could do when it was written", exceptions develop into branch soup, guardrails become straitjackets — and that adaptability belongs in context files the agent reads. The substrate loop decisions must weigh a *hybrid*: deterministic state machine for ownership/claims/gates/delivery (005's original recommendation, matching Stripe blueprints), skill/context files for *how* each agent node works inside its bounded station.
- **Productized validation of the steer-capture/observability decisions (ticket 004)**: skill-activation observability, with/without evals, cost-per-task benchmarking, and drift/overlap findings are exactly the surfaces the owner priced in — shipped commercially here. The registry's "skills as versioned dependencies with install policies + security scoring" is a concrete precedent for capability control (tickets 003/009).
- **The empty slot check**: Tessl is agent-agnostic and organization/multi-project aware, but **does not own the issue-to-merge lifecycle** — issues stay in GitHub/GitLab, Tessl schedules skills around them. The multi-project tracker-neutral control plane remains an open slot in the market.

#### Open-source agent factories (survey run 2026-10-14)

Five open-source systems with real factory shape, none turnkey-complete for Factory's target; the detailed full-pass survey with claim-level primary-source citations is kept at [`docs/research/oss-agent-factories-2026-10-14.md`](../../research/oss-agent-factories-2026-10-14.md). Stars/activity are GitHub API snapshots from 2026-10-14 — weak adoption signals, cited for freshness, not maturity.

| System | It is | Projects / trackers | Permissions / isolation | Known limits (from the projects themselves) |
| --- | --- | --- | --- | --- |
| [Blazity/ai-workflow](https://github.com/Blazity/ai-workflow) (MIT, 13★, active) | Visual typed versioned workflow graph (trigger → clarify/plan → optional plan approval → sandboxed implement → gates → bounded fix loop → PR). Durable run record with per-block prompts/costs/logs. | Repo catalog mixes GitHub + GitLab repos (≤8 per workflow); Jira-only intake; Linear not yet. | Agent blocks in Vercel Sandboxes; enabled-repo list frozen at run start; **never merges** — human reviews/merges. | Vercel-only; narrow adoption; config/version mismatches fail at finalization. |
| [langchain-ai/open-swe](https://github.com/langchain-ai/open-swe) (MIT, ~11k★, very active) | Durable async agent thread per engineering task (investigate → implement → validate → PR); subagents for parallel research; PR review, CI monitoring, schedules. | GitHub issues/PRs, Slack, Linear-as-MCP input; multiple repos per workspace — but workspace preference is explicitly **not an access boundary**. | Per-thread Linux sandboxes in cloud (Daytona/E2B/Modal/local options); local provider **no isolation**, dev-only; GitHub App credentials are installation-wide — workspaces do not partition them; no workspace roles. | README: no external contributions, stability/correctness not guaranteed; CLI path runs locally with host permissions. |
| [vercel-labs/eve-software-factory-template](https://github.com/vercel-labs/eve-software-factory-template) (MIT template, ~1.2k★, maintained) | Fixed four-station team: Classifier → Analyst → Implementer → Reviewer, each own instructions/sandbox/tools; "factory brain" repo memory; ends at draft PR. | One configured repo per deployment; GitHub issues/labels, Linear Agent Sessions, red-CI triggers. | Per-session cloud sandboxes; local TUI treated as untrusted (approval-gated GitHub changes); reviewer sees only the pushed diff. | Single-factory repo by design; known Sep 2026 regression re-cloning per station; approval-gated tools exclusion is convention, not enforcement. |
| [github/gh-aw](https://github.com/github/gh-aw) (MIT, ~5.4k★, very active) | Markdown + YAML frontmatter workflows compiled to pinned GitHub Actions with deterministic jobs: activation, agent, threat detection, safe-outputs. | Repository-centered; cross/multi-repo patterns; experimental Jira/Linear safe outputs. | **Strongest security separation surveyed**: read-only sandboxed agent job; writes buffered as structured artifacts and applied by separate narrow-scope jobs; egress firewall, MCP isolation, secret redaction; security advisory in `0.83.3–0.84.x` already retired. | Depends on GitHub Actions substrate; misconfiguration can defeat assumptions; not a stateful tracker-neutral factory. |
| [OrchestratorInc/agent-orchestrator](https://github.com/OrchestratorInc/agent-orchestrator) (Apache-2.0, ~13k★, very active) | Local daemon supervising multi-project worker sessions — one task, one agent, one worktree per worker; durable facts in SQLite; Kanban derived from observed SCM/CI state; feedback routed back to owning worker. | Multiple projects; GitHub/GitLab observation; opt-in **read-only** issue intake (no commenting/transitions); no Linear. | Worktrees prevent collisions but docs explicitly do **not** treat worktrees as security sandbox — harness runs with host permissions; loopback-bound control daemon. | Local-only (no cloud), tracker lane read-only, no bidirectional sync. |

**What the open-source sample teaches (adopt):** durable inspectable run records as the debug surface; deterministic outer workflow with autonomous inner work; project/repo catalog with **frozen run scope** (the access snapshot frozen and logged at start — the AI Workflow/Open SWE contrast shows both the right and the wrong pattern); isolated per-task workspaces with worktree-vs-sandbox guarantees kept distinct (worktrees ≠ security); independent review over the real diff with cap on self-fix loops; human merge as default policy; budgets/idempotent triggers/bounded retries as first-class.

**Avoid:** workspace labels or preferred repos treated as access controls; installation-wide credentials shared with untrusted issue text; implementer/reviewer sharing private reasoning when independence matters; unbounded self-fix loops or agent-verdict auto-merges; status inferred only from process text or Kanban (keep underlying facts + provenance); a fixed single "software company" pipeline as the one primitive (compose stations instead).

**Verdict reinforced:** across the whole landscape + this open-source sweep, no system yet combines (a) multi-project portfolio scope, (b) tracker-adapter neutrality, (c) capability enforcement outside the prompt, and (d) an authoritative issue→merge loop. Factory's differentiator claim survives.
