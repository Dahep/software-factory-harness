# Open-source agent factories: architecture survey

**Research date: 2026-10-14.** Stars and last-push dates below are GitHub API snapshots retrieved on this date; they are weak adoption/activity signals, not proof of production use. Every architecture claim is cited to a project-owned README, docs page, or source/API endpoint.

Companion detail to the extendend landscape survey in [`docs/wayfinding/closed/005-research-software-factory-landscape.md`](../wayfinding/closed/005-research-software-factory-landscape.md) (see its addendum).

## Verdict

The most useful open-source examples have converged on a recognizable shape: deterministic orchestration owns intake, routing, workspace isolation, checkpoints, test/review gates, and delivery; agents retain autonomy inside a bounded station or run. The projects differ less in agent prompting than in where they put the control plane: a versioned workflow graph (AI Workflow), a fixed role pipeline (Foreman), GitHub Actions plus generated workflows (gh-aw), a durable async agent thread (Open SWE), or a local project/session supervisor (Orchestrator.inc). None is a turnkey multi-tenant, multi-project "software company" with portable issue intake, universal least-privilege isolation, full audit/replay, and automatic merge. The strongest design lessons are to model runs as durable records, make project/repository access explicit, isolate execution per task, keep outputs behind deterministic gates, and leave merge authority with people by default.

## Systems

### 1. Blazity AI Workflow — configurable ticket-to-PR factory

- **Repo and activity:** [Blazity/ai-workflow](https://github.com/Blazity/ai-workflow), MIT. **13 stars**; not a large-adoption signal, but active: GitHub reports a push on **2026-10-09** and the project's docs were last verified 2026-10-09. [Repo metadata](https://api.github.com/repos/Blazity/ai-workflow) · [latest commit](https://api.github.com/repos/Blazity/ai-workflow/commits?per_page=1).
- **Architecture:** A visual, typed, versioned graph defines triggers, agent blocks, branches, bounded loops, and human steps. A durable worker executes deployed graph versions; a dashboard authors them; Neon stores runs and definitions. Typical path: Jira/GitHub/GitLab event → clarify/plan → optional plan approval → sandboxed implementation → repository scripts/leak/review gates → bounded fix loop → PR/MR. It records inputs/outputs per block, exact prompts, costs, logs, and run diagnoses. [README](https://raw.githubusercontent.com/Blazity/ai-workflow/main/README.md) · [workflow-definition contract](https://raw.githubusercontent.com/Blazity/ai-workflow/main/docs/architecture/workflow-definition.md).
- **Projects and trackers:** Repository catalog supports GitHub and GitLab repositories; a workspace can mix them and a workflow may pin up to eight. Intake is Jira-column based, plus GitHub/GitLab PR events, webhooks, schedules, manual dispatch, and MCP. **Linear is explicitly not supported yet** despite being on the roadmap; Jira is the only ticket tracker. [README](https://raw.githubusercontent.com/Blazity/ai-workflow/main/README.md) · [repository scripts/catalog docs](https://raw.githubusercontent.com/Blazity/ai-workflow/main/docs/architecture/repository-scripts.md).
- **Permissions and gates:** Agent blocks run in Vercel Sandboxes, not on operator machines or CI runners. An activated repository catalog restricts dispatch and in-run access; the run freezes its enabled-repository list at start. GitHub/GitLab credentials are stored in the operator's deployment; leak review, configured repository scripts, and review agents can block publication. Plan approval is optional/configurable; **the product never merges PRs**, so a person reviews and merges. [README security and factory line](https://raw.githubusercontent.com/Blazity/ai-workflow/main/README.md) · [factory-building guide](https://raw.githubusercontent.com/Blazity/ai-workflow/main/docs/guides/build-your-software-factory.md).
- **Limitations/failure modes:** Runs only on Vercel today; Jira-only ticket intake; no workflow promotion across teams or organization-wide budgets; no merge step. The docs emphasize configuration/version mismatches can fail at finalization and that repository setup scripts, run ceilings, and multi-repository checks need careful configuration. The workflow graph is intentionally explicit and bounded rather than a free-form "company brain." [README roadmap and limits](https://raw.githubusercontent.com/Blazity/ai-workflow/main/README.md) · [repo scripts failure semantics](https://raw.githubusercontent.com/Blazity/ai-workflow/main/docs/architecture/repository-scripts.md).

### 2. LangChain Open SWE — asynchronous issue-to-PR agent service

- **Repo and activity:** [langchain-ai/open-swe](https://github.com/langchain-ai/open-swe), MIT. **11,021 stars**; active: latest commit/push on **2026-10-14**. The README calls it under active development and warns that breaking changes, rough edges, and correctness/stability gaps remain. [Repo metadata](https://api.github.com/repos/langchain-ai/open-swe) · [latest commit](https://api.github.com/repos/langchain-ai/open-swe/commits?per_page=1).
- **Architecture:** A durable LangGraph thread wraps one engineering agent loop (investigate → implement → validate → deliver PR), with subagents for parallel research/independent work. It also supports separate PR review, CI monitoring, review feedback, schedules, and follow-up work reusing the thread's context and sandbox. Deep Agents provides planning/filesystem/shell/skills/subagents; LangGraph provides durable thread state; Open SWE adds engineering integrations, authorization, and UI. [README](https://raw.githubusercontent.com/langchain-ai/open-swe/main/README.md) · [architecture and configuration](https://raw.githubusercontent.com/langchain-ai/open-swe/main/docs/CUSTOMIZATION.md).
- **Projects and trackers:** Entry points include dashboard, GitHub issues/PR conversations, Slack, and Linear via a configured MCP connection. Workspaces can prefer multiple repositories and route events, but a workspace preference is **not an access boundary**. The workspace doc explicitly says there is no separate dashboard "project" entity. [README](https://raw.githubusercontent.com/langchain-ai/open-swe/main/README.md) · [workspace routing/access design](https://raw.githubusercontent.com/langchain-ai/open-swe/main/docs/reference/workspaces.md).
- **Permissions and isolation:** Default cloud runs use per-thread Linux sandboxes (LangSmith by default; Daytona, Runloop, E2B, Modal and local options exist). The local provider has **no isolation** and is documented as development-only with human-in-the-loop. Coding sandboxes normally receive GitHub App installation-wide access; public-repository event runs and reviewer sandboxes can receive narrower repo-scoped tokens. Workspace roles are not implemented: every signed-in user sees/uses all workspaces, and every admin administers all of them. [README safety section](https://raw.githubusercontent.com/langchain-ai/open-swe/main/README.md) · [sandbox configuration](https://raw.githubusercontent.com/langchain-ai/open-swe/main/docs/CUSTOMIZATION.md) · [workspace security section](https://raw.githubusercontent.com/langchain-ai/open-swe/main/docs/reference/workspaces.md).
- **Limitations/failure modes:** README says no external issues or contributions are being accepted and correctness/stability/compatibility are not guaranteed. Workspace partitioning does not partition installation-wide credentials; member-started coding threads can access all repos available to the GitHub App. The workspace docs enumerate gaps including no workspace roles, per-workspace MCP allowlists for externally triggered runs, or public-safe prompt/output policy. CLI runs execute locally as the user, without sandbox isolation. [README notice](https://raw.githubusercontent.com/langchain-ai/open-swe/main/README.md) · [workspace non-goals and gaps](https://raw.githubusercontent.com/langchain-ai/open-swe/main/docs/reference/workspaces.md) · [CLI caveat](https://raw.githubusercontent.com/langchain-ai/open-swe/main/README.md).

### 3. Vercel eve Software Factory / Foreman — fixed four-station team

- **Repo and activity:** [vercel-labs/eve-software-factory-template](https://github.com/vercel-labs/eve-software-factory-template), MIT template. **1,160 stars**; not archived, with an **2026-09-29** dependency/eve upgrade as the latest commit in the retrieved snapshot. [Repo metadata](https://api.github.com/repos/vercel-labs/eve-software-factory-template) · [latest commit](https://api.github.com/repos/vercel-labs/eve-software-factory-template/commits?per_page=1).
- **Architecture:** A fixed, sequential agent pipeline: **Classifier** (actionability/type/priority) → **Analyst** (plan and acceptance criteria) → **Implementer** (sandbox, repo checks, branch push) → **Reviewer** (independent diff judgment with evidence). Each station has its own instructions, sandbox, and tools; reviewer sees the pushed branch, not implementer reasoning. Repository memory ("factory brain") is shared across runs. [README](https://raw.githubusercontent.com/vercel-labs/eve-software-factory-template/main/README.md) · [Foreman pipeline docs](https://ask-foreman.dev/docs/pipeline).
- **Projects and trackers:** One configured `FACTORY_REPO` per deployment/template instance. GitHub issue label triggers and issue/PR mentions, Linear Agent Sessions, and red CI on the factory's own PRs can start work. It ends with a draft PR; people review and merge. [README configuration and triggers](https://raw.githubusercontent.com/vercel-labs/eve-software-factory-template/main/README.md).
- **Permissions and gates:** Cloud stations work in per-session sandboxes, and branch prefix `factory/` identifies the PRs that automated CI fixes may modify. Local TUI runs are treated as untrusted: GitHub changes wait for user approval. The reviewer is a separate agent over the real diff. [README](https://raw.githubusercontent.com/vercel-labs/eve-software-factory-template/main/README.md).
- **Limitations/failure modes:** Single configured repository constrains it as a multi-project control plane. The Sept. 29 upgrade commit documents a **known performance regression**: each station session now clones the repository and runs setup instead of reusing a prepared template, because the new sandbox API no longer exposes the token-brokering network policy; benefit is dependencies match the branch. It also says that keeping approval-gated tools out of stations is only a project convention—eve does not enforce it, and nobody watches a station's own approval card. [README config](https://raw.githubusercontent.com/vercel-labs/eve-software-factory-template/main/README.md) · [upgrade commit detail](https://github.com/vercel-labs/eve-software-factory-template/commit/6bc5febab95de4c05fa08b164f544650f6aa11aa).

### 4. GitHub Agentic Workflows (`gh-aw`) — declarative automation with staged writes

- **Repo and activity:** [github/gh-aw](https://github.com/github/gh-aw), MIT. **5,398 stars**; active: latest push on **2026-10-14**. [Repo metadata](https://api.github.com/repos/github/gh-aw) · [latest commit](https://api.github.com/repos/github/gh-aw/commits?per_page=1).
- **Architecture:** Workflow author writes Markdown instructions plus YAML frontmatter for triggers, tools, permissions, and engine. `gh aw compile` validates it and generates a pinned `.lock.yml` GitHub Actions workflow. Deterministic Actions jobs handle activation, agent run, threat detection, safe outputs, and conclusion; the agent reasons within its job but does not own the execution graph. Useful patterns include issue triage, PR review, CI investigation, and cross-repository operations. [README](https://raw.githubusercontent.com/github/gh-aw/main/README.md) · [workflow structure](https://github.github.com/gh-aw/reference/workflow-structure/) · [security architecture](https://github.github.com/gh-aw/introduction/architecture/).
- **Projects and trackers:** Primarily repository-centered GitHub Actions automation. Triggers include issues and PRs; safe outputs can create/update issues, PRs, comments and other artifacts. Docs include cross-repository and multi-repository patterns, and experimental integrations for Jira/Linear safe outputs, but this is composed from workflows—not a persistent multi-project dashboard or general ticket queue. [README](https://raw.githubusercontent.com/github/gh-aw/main/README.md) · [safe outputs](https://github.github.com/gh-aw/reference/safe-outputs/).
- **Permissions and gates:** Strongest security separation in this sample: agent job is read-only and sandboxed; writes are buffered as structured artifacts, filtered and applied in separate jobs with narrow scopes. The stack adds Docker/network isolation (or preview microVM), an egress firewall, MCP server isolation, input sanitization, secret redaction, integrity filtering, and compilation-time checks. [README security summary](https://raw.githubusercontent.com/github/gh-aw/main/README.md) · [security architecture](https://github.github.com/gh-aw/introduction/architecture/) · [safe outputs](https://github.github.com/gh-aw/reference/safe-outputs/).
- **Limitations/failure modes:** Project docs caution that misconfiguration, overly permissive workflow definitions, and failures of trusted substrate/configuration can defeat assumptions; even careful human supervision does not prevent all failures. The README notes a security advisory affecting versions `>=0.83.3,<0.85.4`, whose releases were retired. Current operation depends on GitHub Actions and its workflow/tool ecosystem; it is powerful automation infrastructure, not a stateful, tracker-neutral software company. [README warning](https://raw.githubusercontent.com/github/gh-aw/main/README.md) · [security threat model](https://github.github.com/gh-aw/introduction/architecture/).

### 5. Orchestrator.inc (`agent-orchestrator`) — local multi-project worker supervisor

- **Repo and activity:** [OrchestratorInc/agent-orchestrator](https://github.com/OrchestratorInc/agent-orchestrator), Apache-2.0. **13,179 stars**; active: latest commit/push on **2026-10-14**. [Repo metadata](https://api.github.com/repos/OrchestratorInc/agent-orchestrator) · [latest commit](https://api.github.com/repos/OrchestratorInc/agent-orchestrator/commits?per_page=1).
- **Architecture:** A project-aware orchestrator turns goals into focused worker sessions; each worker owns one task, one coding agent, and one workspace. A long-running local daemon observes runtime and SCM facts, stores durable facts in SQLite, and derives displayed status from them. Each Git-backed worker gets a branch/worktree; a live Kanban tracks agent, PR, CI, and review state. Actionable PR/CI/review feedback is routed back to the owning worker. This is primarily a supervisor for multiple sessions, rather than a forced classifier→planner→coder→reviewer line. [README](https://raw.githubusercontent.com/OrchestratorInc/agent-orchestrator/main/README.md) · [architecture](https://raw.githubusercontent.com/OrchestratorInc/agent-orchestrator/main/docs/architecture.md).
- **Projects and trackers:** Supports multiple projects and GitHub/GitLab SCM observation. Opt-in GitHub/GitLab issue intake can spawn workers, but the tracker lane is explicitly read-only: it does not comment or transition issues; Linear and external tracker plugins are unsupported. PR/CI/review facts are separate from issue intake. [README](https://raw.githubusercontent.com/OrchestratorInc/agent-orchestrator/main/README.md) · [tracker docs](https://docs.orchestrator.inc/plugins/trackers) · [SCM docs](https://docs.orchestrator.inc/plugins/scm).
- **Permissions and isolation:** Per-session Git worktrees prevent branch/file collisions; the daemon launches local native PTY/ConPTY or Chat controllers and uses installed agent credentials. Docs do **not** describe the worktree as an OS security sandbox; reviewer modes/prompt instructions likewise do not sandbox tools or network. Treat the harness's permissions as the effective host permissions. LAN/mobile control is opt-in and authenticated; the local control daemon is loopback-bound by default. [architecture](https://raw.githubusercontent.com/OrchestratorInc/agent-orchestrator/main/docs/architecture.md) · [agent adapter docs](https://docs.orchestrator.inc/plugins/agents).
- **Limitations/failure modes:** Issue intake is opt-in/read-only and not full bidirectional tracker synchronization. The project docs emphasize conservative lifecycle handling: failed runtime probes are not proof a process died; dirty worktrees must not be force-deleted; display status is derived rather than directly stored. The architecture is rich in observability/recovery but depends on local daemon, agent installs, credentials, and SCM availability. [tracker docs](https://docs.orchestrator.inc/plugins/trackers) · [architecture load-bearing rules](https://raw.githubusercontent.com/OrchestratorInc/agent-orchestrator/main/docs/architecture.md).

## Structural recommendations for a multi-project Factory control plane

### Adopt

1. **A durable, inspectable run record.** Store triggers, resolved project/repository scope, graph/workflow version, agent/provider, timestamps, checkpoints, outputs, gates, budget, and terminal reason. Make the event trace/replay the primary debugging interface (AI Workflow, Open SWE, Orchestrator).
2. **A deterministic outer workflow with autonomous inner work.** Keep routing, loop bounds, cancel/resume, approvals, validation, and delivery as explicit state transitions. Use the model for interpretation and code changes, not as the only source of workflow truth (AI Workflow, gh-aw).
3. **Project/repository catalog with frozen run scope.** Make allowed repositories and credentials first-class. Freeze the access snapshot at run start, log it, and require explicit catalog enablement; do not confuse a "preferred/default repository" with a security boundary (AI Workflow and Open SWE show both patterns).
4. **Per-task isolated workspaces and explicit lifecycle facts.** Worktrees solve concurrency collisions; sandbox boundaries solve host/security exposure. Keep those guarantees distinct. Derive user-facing status from observed durable facts and avoid marking workers dead on a failed probe (Orchestrator).
5. **Independent verification and staged side effects.** Use repository-owned checks plus independent review, cap fix loops, make publication a gate, and separate agent write requests from credentials that apply them (Foreman, AI Workflow, gh-aw).
6. **Human merge as the default policy.** Make plan approval and review checkpoints risk-configurable; have the Factory produce a reviewed draft PR and leave merge as a deliberately separate authority (Foreman, AI Workflow).
7. **Operational controls.** Per-run duration/token/cost budgets, idempotent triggers, duplicate prevention, bounded retries, transparent error categories, logs, exact prompt provenance, and a queue/worker view are part of the factory, not post-launch extras.

### Avoid

- Treating workspace labels, preferred repos, Git worktrees, or prompt instructions as access controls.
- Sharing installation-wide credentials with untrusted issue/PR content unless the blast radius is intentionally accepted.
- Letting implementer and reviewer share private reasoning/context when independence matters.
- Unbounded self-fix loops, agent-controlled direct writes, or silently auto-merging based on an agent verdict.
- Implicit state inferred only from process text or a Kanban status; preserve the underlying facts and their provenance.
- Starting with one fixed "software company" pipeline as the only primitive. Provide composable stations and deterministic workflow definitions, with a standard issue→PR template.
- Treating stars or "active" repository status as operational maturity; explicitly record license, maintenance, known gaps, and security caveats.

## Excluded-in-review

Per request, this survey does not re-cover MetaGPT, ChatDev, AutoGen/AG2, OpenAI Agents SDK, Anthropic multi-agent writeups, Devin/Cognition, Cursor agents, Stripe Minions, GitHub Copilot coding agent, Google Jules, OpenHands, SWE-agent/mini-swe-agent, T3 Code, pi.dev, Paperclip, mattpocock/skills, Factory.ai, or the other closed-source products named in the brief.
