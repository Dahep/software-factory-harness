## Question

Two major harnesses now expose **code mode** — the model writes a program that composes tool calls, instead of calling tools one round trip at a time. Companion to [Study Swamp Club's behavior-centric design](closed/013-research-swamp-club-behavior-centric.md): Swamp packages *durable, registry-backed behaviors*; code mode composes *ephemeral, per-step* calls in code. Study both implementations and extract what Factory should adopt, adapt, or avoid:

1. **Exact mechanics.** (a) **Claude Code Code Mode** — experimental since 2.1.323 (Nov 2026), off by default, enabled via env var, cannot be enabled per-project; model writes JavaScript "that makes the tool calls," runs "in your session"; documented provider restrictions (not on Bedrock/Vertex/Foundry/custom gateways); the "who checks the calls" question. (b) **Pi Codemode** — Pi 1.0 (Oct 1, 2026): embedded QuickJS-in-WASM sandbox, tools as code APIs with deferred exposure (`searchTools()`, `describeTool()`, inline token budget), scripts can call non-LLM models directly, state in session transcript; the design decision that the sandbox lives in the harness not the server (composition across vendors); Armin Ronacher's writeup. Get primary sources for both (Claude docs, Pi docs, release notes) before third-party commentary.
2. **The three-way comparison** — Swamp behaviors vs code mode vs closed/011's Go-owned typed workflow graph. Where does each sit on the durability/determinism spectrum? Is "workflow code" in Factory really the same object as code-mode scripts (LLM-authored, ephemeral, unverified) — or the opposite (typed graph, engine-owned, replayable)? Name the boundary precisely; a conflation would poison the spec.
3. **Factory implications.** Should Factory expose its primitives (issue/task/agent/gate/tracker ops) as **code APIs inside agent sessions** — i.e. code mode *inside* the RuntimeAdapter, so agents can compose Factory calls cheaply — while the typed graph stays the durable orchestration layer? What does that mean for the RuntimeAdapter contract (ticket 006), the loop's implementer/reviewer wave (008), and capability control (009 — a sandboxed JS surface is a permission boundary, per Pi's no-filesystem/no-network constraints)?
4. **Measurement (directive #15).** Code mode's pitch is fewer round trips and less context; what published evidence is there (token savings, latency, filtering examples), what is unmeasured hand-waving, and what metrics would Factory track if it adopted the pattern? Note Ronacher's own caution that composition gains depend on the API shape.
5. **Maturity and risk.** Experimental vs shipped, model/plan restrictions, community pushback (Pi's MCP reversal and codemode criticism), security model (sandbox limits, what the caller can see) as of 2026-11-18.

Verdict must state: per-concept adopt/adapt/avoid with reasons, the precise boundary between code-mode composition and Factory's typed graph, which map tickets (006, 008, 009, closed/011, closed/013) are touched and whether any should re-open or reshape, and what Factory measures first. Date claims 2026-11-18; primary docs and release notes over aggregators.

## Resolution

**Research snapshot: 2026-11-18.** Both primary doc sets were fetched in full the day of writing: the official Claude Code Code Mode page (code.claude.com/docs/en/code-mode), the official Pi Codemode, MCP, and CLI pages (pi.dev/docs/latest), both vendors' release notes (Claude Code v2.1.323 of 2026-11-12 and v2.1.326 of 2026-11-16; Pi 1.0.0 of 2026-10-01), Earendil's own MCP-reversal post, and Ronacher's write-up. All four designated third-party write-ups were read — one (dan.avila7 on Medium) is member-gated and yielded only its visible claims; one (mindstudio.ai) contains factual drift against the primary docs (it names "Opus 4.5 / Sonnet 4.5" where the docs say Opus 5.5 / Sonnet 5.5), which is itself the lesson: cite the docs, not the aggregators. Measurement claims were traced to their methods; where a number has no published method, the resolution says so.

**Headline.** Code mode is real, converging, and *not* what Factory's workflow layer is. Two very different harnesses — Anthropic's Claude Code (experimental, Nov 2026) and Earendil's Pi (shipped in 1.0, Oct 2026) — plus Cloudflare and Anthropic's API teams independently landed the same pattern: the model writes a script that composes tool calls, the script runs once in a constrained runtime on the **harness** side, and only the distilled result re-enters the model's context. The published evidence supports it as a **context-economy pattern** (tool-definition overhead and intermediate-result bloat shrink dramatically; task-level savings are real but far smaller and shape-dependent), and it arrives with an explicit durability warning from its own best-known advocate: Ronacher muses that durability "is trickier" and that "maybe, something like Starlark is a better composition language than JavaScript given its deterministic nature" — an unplanned echo of closed/011's decision. For Factory the verdict is: **adopt the pattern as an in-session composition surface over Factory primitives (sandboxed, tool-only reach, per-call permission checks), keep the typed graph as the sole durable orchestration layer, and treat every LLM-authored script as ephemeral — never typed, never replayed, never a gate.**

### 1. Exact mechanics

#### (a) Claude Code Code Mode — experimental, gated, permission-checked after the fact

**What runs where.** Without Code Mode, Claude asks for one tool call (Bash, Read, Edit), waits, reads the result, and decides next — one model round trip per call. With Code Mode, Claude writes a piece of JavaScript that makes the tool calls, and **Claude Code runs that code in your session**. The code is the input to a tool named `REPL`; inside it, calls chain (`await $`…`` for shell, `edit(…)`, `file(f).text()`), independent calls run concurrently (`Promise.all`), and the last expression returned is what Claude reads. In the conversation the user sees the tool calls and diffs, not the code; the code appears as collapsed **Code** rows in the transcript viewer (Ctrl+O). There is **no WASM/QuickJS sandbox**: the script runs on the session host with the harness's own privileges — the security model is entirely the permission system, not process isolation.

**Enablement and gates (all from the official docs).** Experimental, **off by default**, "may change or be removed in any release." Enabled by env var `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1` in the shell or **user** settings (`~/.claude/settings.json`); Claude Code **ignores the variable in project settings**, so a cloned repository cannot enable it — and an organization can block it for everyone via managed settings (value `0`) but **cannot force-enable it**; there is no per-project enablement. Additional gates: Claude Code v2.1.323+ (the 2026-11-12 release) on the **native build**; a direct Anthropic subscription/Console account — **not** through a gateway, Amazon Bedrock, Claude Platform on AWS, Google Cloud's Agent Platform, Microsoft Foundry, or Claude Models on Google Cloud; no HIPAA or zero-data-retention org settings; only Claude Opus 5.5, Sonnet 5.5, Haiku 5.5, or Fable 5.2; an **interactive terminal session only** — no `-p`, no Agent SDK, no VS Code panel, no Desktop app, no cloud sessions; cannot start with an API key helper, OpenTelemetry export, or `DISABLE_TELEMETRY`; certain plugins/mods block it; agent teams need v2.1.326 (2026-11-16). Resuming a Code Mode session requires the variable still set. While in it, you lose Remote Control, Claude in Chrome, and computer use.

**"Who checks the calls" — the documented regime.** Every tool call inside the code still goes through the user's `deny`/`ask` permission rules and `PreToolUse` hooks **under the tool's usual name** (e.g. `Bash`) — so per-call checks survive. Beyond that: in **auto mode, a classifier reviews each piece of code before it runs — not each tool call** — and the docs are explicit about the blind spot: "It doesn't see values computed at run time, such as a path taken from search output, so keep rules or hooks for calls you must control." In other permission modes the code starts un-reviewed and the user is prompted per call that would prompt. Hook authors get two sharp warnings: a shell command can reach hooks with a `cd` prefix (`cd 'app' && git push`), so text-matching rules must inspect each part of a compound command; and to inspect the script itself a hook matches the `REPL` tool and reads `tool_input.code`. Failed or timed-out hooks **refuse** the call (even with `onFailure` unset), and once Claude has run code in a session, hook timeouts refuse any other call too. The docs themselves route limits that must not depend on command text to sandboxing — an admission that Bash text rules are not the boundary.

**Long-running code.** Waiting mode stops after ten minutes (including time spent at permission prompts); **background mode** — only when the session started in auto or `bypassPermissions` mode — lets code run up to two hours while the user keeps talking to Claude. New code starting while earlier code runs in auto mode costs the earlier code its classifier review and triggers a permission prompt with a countdown.

**Early churn (release evidence).** Post-2.1.323 releases fixed: Code Mode scripts ignoring a worktree entered with `EnterWorktree`, writing `~` paths into the project, stale `/mcp` state, words typed at permission dialogs not reaching Claude, and Claude starting work by itself when resuming a session that ended mid-script. Fresh feature, moving edges.

#### (b) Pi Codemode — shipped, sandboxed, transcript-stated

**What runs where — the brains/hands split.** Ronacher's framing, now first-party doctrine at Earendil: there are two systems — the **brain** (the harness, trusted, where the agent loop runs) and the **hands** (the execution environment where bash and tools run, untrusted, possibly sandboxed). Codemode runs on the **harness side, in its own sandbox**: QuickJS compiled to WASM, with **no Node APIs, no file system, no network, no timers, and 256 MB of VM memory** — "the only way is to call more tools." Because it runs on the harness side, **its state is maintained as part of the session transcript instead of the file system**. This is the design decision the ticket flags: the sandbox lives in the harness, not in any server or vendor — so Pi composes tools from **any** provider (15+ providers, MIT-licensed), while Claude Code's equivalent is locked to Anthropic's own API.

**Scripts.** The `codemode` tool's input is raw JavaScript source that runs as the body of an async function — top-level `await` and `return` work. Globals: `tools.<name>(args)` (every callable tool as a method; MCP tools named `mcp__<server>__<tool>`), `text()`, `image()`, `console`, `store(key,value)`/`load(key)`, `ALL_TOOLS`, `searchTools(query)` (BM25 ranking, default limit 8), `describeTool(name)` (full TypeScript declaration), `describeNamespace(name)`, and `models`. An options line (`// @options: {"max_output_tokens": …, "timeout_ms": …}`) caps output (default 10,000 tokens; overflow keeps start/end and writes full text to a temp file) and sets a hard deadline. A failing script keeps its partial output; **tool calls are real — calls made before a failure are not undone**, and unawaited promises are discarded.

**Deferred exposure and the inline budget.** The `codemode` description lists tools with TypeScript declarations that share a **budget of 3,000 estimated tokens** (`codemode.inlineBudget`); tools with `deferred` exposure — which includes every MCP tool under the default `codemode` exposure — are **not listed**, so the description stays the same while MCP servers connect. Scripts discover the rest via `searchTools()`/`describeTool()`/`ALL_TOOLS`. This is progressive disclosure built into the tool surface, not a prompt-engineering trick.

**Exposure modes (`on`/`only` and friends).** Each tool has an exposure: `codemode` (default for MCP: callable from scripts, never declared to the model), `deferred` (declared only after `tool_search` loads it), `direct` (declared to the model *and* script-callable), `hidden` (registered, unreachable). While codemode is active, `codemode.mode` decides how the other tools are presented: `on` (default — declared tools stay declared) or **`only`** — the other tools are hidden from the model entirely and listed in the codemode description instead, making scripts the *only* path. `--tools read,codemode` keeps every MCP tool script-callable without declaring any of them. Exposure is **per-tool capability metadata** — exactly the shape Factory's capability model needs (§3).

**Non-LLM model calls inside scripts.** `models.classify(model, context)` and `models.generateImages(model, context)` run **classifier and image models with the session's credentials** — models that "would just waste context" as regular tools (Ronacher). Chat models are listed but cannot be run from scripts. At most four such calls run concurrently per script; usage is added to the codemode result and counts toward session cost. Earendil's own demo: 167 Linear issues fetched via MCP, classified by the Jev classifier four-at-a-time, sorted, filtered, and **only the summary** returned to the model — with the per-issue verdicts stashed via `store()` for later digging without re-fetching.

**State location and its semantics.** `store()`/`load()` keep small JSON values (≤256 KiB per value, ≤1 MiB total) across codemode calls; writes persist only when the script succeeds, by appending a `codemode-store` custom entry to the **session transcript** — so resumed sessions keep the values, and each session branch sees only the values written on its path. State is durable-within-a-session, transcript-versioned, and zero-filesystem.

**Resource governance.** Max two codemode workers per pi process (`PI_CODEMODE_MAX_WORKERS`); at capacity, scripts queue FIFO and fail after 60 s without a worker; a script waiting on a promise that can never settle fails immediately (no timers); scripts cannot start other codemode scripts; bash called from a script resolves to a structured `{output, truncated, full_output_path?, exit_code, wall_time_seconds}` with up to 1 MiB of output — versus the trailing 2,000 lines / 50 KB the model would see from a direct bash call. Output caps: 16,777,216 characters and 100,000 output calls, ever.

**The MCP reversal, first-party.** Pi's homepage used to declare it does not support MCP; creator Mario Zechner had dismissed it for over a year with concrete numbers (one popular server: 21 tool definitions, 13,700 tokens every session). On 2026-09-29, Pi 0.99.0 shipped MCP as a core feature with a self-aware post titled "You Said No MCP!" Their stated reasons: MCP itself changed (July 2026 spec, stateless-first; donated to the Linux Foundation Dec 2025; 17,000+ public servers), the changes MCP required were **generally useful** ("the changes we have made to MCP also enable the use of Jev more easily within Pi… Ultimately what Pi needs is quite similar to what MCP needs: a sandbox to play with in the form of an interpreter"), and "we believe the best way to positively influence something is to embrace it." Pi 1.0 followed on 2026-10-01 with codemode as a headline feature and Pi Durable — a separate, explicitly **experimental** package — for long-running durable agents with checkpointed tasks.

### 2. The three-way comparison — and the boundary that must not be crossed

Three objects share the word "workflow" and must never be conflated:

| Axis | closed/011 typed graph (decided) | Swamp behaviors (closed/013) | Code mode (this ticket) |
| --- | --- | --- | --- |
| Who authors | Human/agent authors **typed data** (Dhall/JSON/YAML over the IR) | Human/agent authors YAML definitions validated against typed zod schemas | **The LLM writes code**, unreviewed, in the moment |
| What it is | Go-owned, versioned **typed IR**; engine-interpreted | Engine-interpreted YAML DAG of typed behaviors | **Ephemeral JavaScript**, executed once |
| Typing | Typed step inputs/outputs; CEL guards | JSON-Schema boundary + zod types | **None** — untyped JS, output is whatever the script returns |
| Verification | Validated before execution (refs, schemas, bounds) | `swamp validate` checklist, schema-validated artifacts | **Only by running it**; no type check, no linter, no review step |
| Durability | Fully durable: versioned, replayable, engine owns retries/approvals/state | Durable: versioned, lockfile-pinned, checksummed artifacts | **None across sessions**: transcript-visible at best (Pi: `store()`; Claude: transcript viewer), gone when the session dies |
| Determinism | Engine semantics (declared retry, approval nodes, guarded skips) | Engine semantics + documented fail-continue gap | **Best-effort**: real tool calls not undone on failure, unawaited promises discarded, ten-minute/hour limits, worker queues |
| Lifetime | Run → history → replay | Run → versioned data artifacts | One script execution |
| Who can compose | Engine + author | Engine + behaviors | **One agent, inside one session, right now** |

**The precise boundary statement.** Code-mode scripts and the typed graph are **opposites on the durability/determinism spectrum, not the same object at different scales**. A code-mode script is LLM-authored, untyped, unverified, executed once, never versioned, never replayed, and its only trace is a transcript entry; it is a *session-internal composition accelerator* for one agent's tool calls. The typed graph is engine-owned, typed, validated before execution, versioned, replayable, and its semantics (retry, approval, guards) are fields the engine — not the author's cleverness — enforces. Between them sits the middle layer both Swamp and Pi corroborate: **typed, versioned, registry/schema-backed primitives** (Swamp behaviors; Factory's issue/task/agent/gate/tracker ops) that the graph orchestrates across runs and that scripts can compose within a run. Ronacher — the best-placed observer alive — reached the same conclusion unprompted: durability with codemode "is trickier," maybe durable-workflow-engine ideas are needed, "or maybe, something like Starlark is a better composition language than JavaScript given its deterministic nature." Swamp says it in its own vocabulary: definitions are "**data, not code** — an agent produces them by writing YAML that conforms to the type's schema."

**A conflation would poison the spec** in one specific way: if Factory's spec treated "workflow code" as one category, an implementer agent's throwaway script and the owner's reviewed, versioned loop definition would share a trust level, a verification bar, and a change-control story — and neither would get the one it needs. The warning the ticket asked for, made concrete: **an LLM-authored code-mode script is never the typed graph, never part of it, and never executes in its place. The only path from script to graph is promotion: a human-reviewed (or gate-reviewed) translation of the script's proven logic into a typed step or behavior, which then carries the graph's guarantees.** Anything the issue-driven loop must *depend on* — a gate, a retry, an approval, an evidence record — lives in the graph or the typed primitives, never in a script that only exists because a model felt like writing one.

### 3. Factory implications — code APIs inside agent sessions, graph on top

**Yes: expose Factory's primitives as code APIs inside agent sessions; no: never as the orchestration layer.** The three tickets reshape as follows.

**006 (RuntimeAdapter) — add a composition-surface requirement.** The adapter's contract should gain one optional-but-designed capability: a **sandboxed script surface over Factory's primitive APIs** (issue/task/agent/gate/tracker ops), following Pi's reference design — no ambient filesystem or network, reach only through the exposed tools and a models API, structured outputs, deferred discovery with an inline token budget, and per-call capability checks. Two design facts make this cheap to own rather than rent: Pi's precedent that **the sandbox lives in the harness, not the server**, so Factory can ship one sandbox that composes over *any* runtime behind the adapter (OpenCode today, others later), instead of waiting for each runtime to grow its own code mode; and the fact that Factory's own runtime choice (002's hybrid) makes Factory the harness. Three contract requirements follow from the vendors' documented mistakes: (i) primitives need **structured, schema-declared outputs** — Ronacher's top MCP complaint is servers that return token-optimized text, so Factory's adapter API must return typed data, never prose; (ii) primitives need **exposure metadata** (direct / deferred / script-only / hidden) as part of their declaration, since Pi needed exactly this metadata upgrade to make deferred loading work; (iii) the surface must degrade gracefully — code mode is an accelerator, and every composition expressible in a script must remain expressible as sequential tool calls, so nothing in the loop can *require* it.

**008 (issue-driven loop wave) — composition inside agents, structure stays in the graph.** Code mode changes the *inside* of agent steps, not the shape of the wave. Steps where one agent makes many similar calls — the triage sweep over an issue backlog, evidence collection across a diff, aggregating N review verdicts — become candidates for script composition (Pi's own demo is literally "classify 167 tracker issues and return the summary"), with the expected wins in round trips and context. What does **not** move: the wave's structure (N implementers, M reviewers, the gate), approval suspension and resume, retry semantics, and anything that outlives one agent's turn — all of that is graph territory and stays engine-owned per closed/011 and the 014 rule that a gate can never live in an LLM-interpreted file (a script is exactly such a file). The loop should also never *depend on* a script for correctness: if a script's result matters, its method gets promoted into a typed step or behavior.

**009 (capability control) — the sandbox is the boundary, and the per-call check survives.** Pi's sandbox is the strongest new precedent for 009: because the script can reach the outside world **only through tools**, the tool layer *is* the permission surface — no-FS/no-network composition is a real permission boundary, not just a performance device. That composes with Swamp's default-deny grant model (already fed to 009 by closed/013): a role profile becomes exposure modes plus grants — these primitives are `direct` for the implementer, `script-only` for the triager, `hidden` from the reviewer. The Claude Code docs contribute the negative result 009 should encode: **auto mode's classifier reviews each script once and "doesn't see values computed at run time"** — Anthropic's own docs instruct users to keep rules and hooks for anything they must control. Factory must therefore check every call at the tool layer inside scripts (as Claude Code in fact does for rules/hooks under the tool's usual name), and must not adopt a "review the code, trust the run" model. Pi adds the resource dimension: script-level budgets (output tokens, timeout, worker caps, per-model-call concurrency, cost counted per call) are grant parameters 009 should carry — cost budgets inside the sandbox, mirroring Swamp's CEL cost budgets.

### 4. Measurement — what is evidence, what is pitch

**Published numbers, sorted by method quality (the developed world's Code Mode numbers each measure something different):**

| Claim | Who | What it actually measures | Method |
| --- | --- | --- | --- |
| 99.9% (1.17M → ~1,100 tokens) | Cloudflare, 2026-02-20 | **Tool-definition tokens only**, for its own 2,500+ endpoint API | tiktoken count, published — the only Code Mode figure with a method |
| 94% (9,400 → 600 tokens) | Cloudflare, 2026-04-14 | Tool-definition tokens for 52 tools across 4 internal MCP servers | Published; cost stays fixed as servers grow |
| 98.7% (150K → 2K tokens) | Anthropic, 2025-11-04 | One illustrative Google Drive→Salesforce example | **A calculated example, not a measured benchmark** |
| 37% (43,588 → 27,297 tokens avg) | Anthropic (Programmatic Tool Calling) | **Full-task tokens** on complex research tasks | Measured; the honest benchmark shape |
| ~40% (5,300 → 3,300 tokens) | Pi 1.0.0 release notes | **Prompt overhead** of one GPT-5.6 request with codemode active | Vendor-reported; prompt cost, not task outcomes |
| 35s → 15s; 17s → 14s | flaviocopes hands-on, 2026-11-18 | Two same-task A/B runs on one small project | Self-flagged: "single runs on one project, not a benchmark" |
| 13 calls in 2 model turns | dan.avila7, 2026-11-16 | One broken-links task | Anecdote (member-gated post) |

**The honest reading.** The pattern's *definition-cost* win is proven and structural: tool-definition overhead collapses and stays flat as the tool surface grows. The *task-level* win is real but modest and shape-dependent — Anthropic's best measured full-task number is 37%, not 98.7%; and the round-trip win accrues **only on dependent chains and repeated similar calls**: Claude Code already runs independent calls in parallel without Code Mode, which is why flaviocopes' parallel-checks comparison was nearly a wash (17s→14s) while the 100-build loop (101 shell commands, one script, user answered a separate question meanwhile) was transformative. Two documented caveats belong on Factory's ledger: Anthropic's own warning that code execution "adds operational overhead and security considerations that direct tool calls avoid," and the recurring finding that turning it on does not guarantee lower cost or faster turns — script generation and reasoning still bill.

**Ronacher's caveat, verbatim in substance.** Composition gains depend on the **API shape**: he asks MCP servers for structured content (`outputSchema`), **consistent results regardless of batch size** (a 5-item probe can succeed while the full batch fails when a server token-optimizes), large-binary support, and composable tool search across servers. Cloudflare's own servers wrapping their inner code mode produce "Codemode in Codemode" — double JSON escaping, "easy for smaller models to get confused by," and the inner code cannot call the outer tools. For Factory this is a first-order API-design requirement, not a footnote: **Factory's primitive API shape determines whether its code-mode surface is a win or a tar pit.**

**What Factory would track first (directive #15), per workflow step where the surface is enabled:** (1) **model round trips per unit of work** (calls → scripts ratio; the round-trip reduction is the pitch's testable core); (2) **prompt-definition tokens per session** (the Pi-40%/Cloudflare-99.9% axis — cheap, structural, and flat); (3) **full-task tokens and wall time, A/B against the same step run without scripts** (the Anthropic-37% axis; flaviocopes-style same-task pairs, never single-run anecdotes); (4) **script failure and refusal rates** (scripts that hit permission refusals, hook failures, output caps, worker queues — the cost the pattern adds); (5) **script reuse and promotion rate** — how often a script's logic graduates into a typed behavior or graph step, which measures the boundary from §2 in practice; (6) cost of non-LLM model calls from scripts, per call (Pi counts these toward session cost; Factory should budget them like any grant). None of these exist in either vendor's docs as first-class metrics — Factory measuring them would be ahead of both.

### 5. Maturity and risk, as of 2026-11-18

- **Claude Code: experimental and heavily gated.** Off by default, "may change or be removed in any release," opt-in only via user-level env var, orgs can block but not enable; direct-Anthropic-API only (no Bedrock/Vertex/Foundry/gateways/custom base URLs), four specific Claude models, interactive terminal only; a documented classifier blind spot in auto mode; post-release churn fixes (worktree, `~` paths, resume behavior). Usable evidence, **not a substrate to copy controls from**.
- **Pi: shipped in 1.0, architecturally committed.** Codemode is core to Pi 1.0 (2026-10-01), MIT-licensed, provider-neutral, and Pi needed it anyway for the MCP reversal ("integration was nearly free… the harness needed a JavaScript sandbox for Codemode anyway"). The *durability* layer around it — Pi Durable, checkpointing and replay — is explicitly experimental; the QuickJS sandbox constraints (256 MB, two workers, no timers) are real limits, and the docs note a Bun-specific edge where a non-polling built-in can outlive a cancel.
- **Community pushback is about the MCP reversal, not the pattern.** The HN debate (hundreds of points within hours of 0.99.0) split between a "capitulation" reading and "the cost problem got a real solution" reading; Earendil's own post concedes "quite a few have not" improved about MCP and that "MCP continues to be hard to compose" even with codemode. Ronacher's MCP-desires list (structured content, consistent results, binary data, composable search) is the pattern's honest bug list. Cloudflare's numbers carry their own inconsistency (intro says "over 2 million" tokens; body says 1.17M).
- **Security models are asymmetric and neither is sufficient alone.** Claude Code: script runs with harness privileges; the boundary is permission rules + hooks + (auto mode) a classifier that provably cannot see runtime-computed values; the docs route text-independent limits to sandboxing. Pi: process isolation via WASM (no FS/network/timers) but the harness itself remains fully trusted, and store() state lives in the transcript. Anthropic's own engineering post warns that running agent-generated code "requires a secure execution environment with appropriate sandboxing, resource limits, and monitoring." Factory's translation: **sandbox + per-call capability checks + resource budgets, all harness-owned** — take Pi's isolation, Claude Code's per-call rule retention, and reject both vendors' shortcuts (classifier-only review; full-trust execution).

The only bridge is **promotion** (script logic → reviewed typed step/behavior). See §2 boundary statement; Ronacher's Starlark remark and Swamp's "definitions are data, not code" both point the same way. |
| 6 | **Claude Code's enablement/gating shape** (user-only env var, API/model lock-in, surface restrictions) | **Avoid copying; note as maturity risk** | The lock-in is a vendor's product decision (direct API only), not a design lesson; the user-only enablement *is* a good security default (a cloned repo cannot enable it) worth keeping as a Factory config rule. |

**The boundary, stated once more for the spec:** *Factory's typed graph orchestrates durable, typed, versioned steps and behaviors across runs; code mode lets one agent compose calls to those same typed primitives within one session; a script is an ephemeral accelerant, never an artifact of record, never a gate, and never part of the graph — the path from script to graph is promotion through typing and review, and only promotion earns the graph's guarantees.*

### Impacts on the map

- **006 (harness substrate) — reshape, do not re-open.** Add to the RuntimeAdapter contract: (a) an optional, Factory-owned sandboxed script surface over Factory primitives (Pi's design: harness-side sandbox, tools-only reach, deferred discovery, structured outputs) that works over whatever runtime 002's hybrid selects — Pi's "sandbox lives in the harness, not the server" makes this runtime-independent; (b) exposure metadata (direct/deferred/script-only/hidden) on the adapter's tool declarations; (c) structured, schema-declared outputs from every primitive (Ronacher's MCP lesson applied to Factory's own API shape); (d) graceful degradation — no loop step may require the script surface.
- **008 (issue-driven loop) — reshape, no re-open.** Inside-step composition (triage sweeps, evidence collection, review-verdict aggregation) becomes the designed use of the surface, with the wave's implementer/reviewer structure, gates, approvals, and retries unchanged and engine-owned. Re-affirm the 014 rule in script terms: a merge gate can never be an LLM-authored script. The measurement list from §4 should land in 008's milestone-1 observability requirements.
- **009 (capability control) — reshape.** Add Pi's sandbox as the concrete precedent that a no-FS/no-network script surface *is* a permission boundary; compose it with closed/013's grant vocabulary: profiles = named grant bundles **plus exposure modes** (direct/deferred/script-only/hidden); add script-level resource budgets (output tokens, timeout, worker/concurrency caps, per-call model cost) as grant parameters; encode the Claude Code negative result — capability checks are per-call at the tool layer, never "review the code once."
- **closed/011 (typed graph + CEL) — no re-open; strengthened.** The designer of the leading code-mode implementation independently flags JS composition as non-deterministic and reaches for a deterministic language; Swamp's engine independently converged on the same typed-graph shape. No reopen trigger fires. One forward note for the successor ergonomics ticket (post-008): if Factory's in-session surface ever needs a *deterministic* restricted language, that is a CEL-adjacent or Starlark-shaped call to make there — it changes nothing about the IR.
- **closed/013 (Swamp) — no re-open; complement confirmed.** The three layers now line up across all three studies: typed primitives (Swamp behaviors = Factory's code-API surface), engine-owned graphs (Swamp workflows = closed/011), session-internal composition (code mode = what drives the primitives inside one agent's turn). `@swamp/software-factory` remains the cautionary ceiling: its driving agent composes calls with **zero harness control**; Factory's script surface must sit *inside* the capability-controlled harness — the sandbox's reach is the grant model, not the agent's whims. Swamp's `describe --json`/`search --json` discovery bar now has a second independent corroboration in Pi's `describeTool()`/`searchTools()` — machine-readable discovery is the settled ergonomics requirement for the successor ticket.
