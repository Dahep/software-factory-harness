## Question

Owner direction (2026-11-18): Factory should gain a **sandboxing layer** using **devvm** (installed here via mise, `github-devvmhq-devvm` 0.1.0) — plausibly **one devvm per workflow-executing thread/process** — with **secrets configured per project**, requested per thread and injected by the sandbox rather than handed to the agent. Research devvm and decide whether Factory's spec should commit to it as the isolation/secret substrate.

1. **Programmatic lifecycle.** devvm is a folder-scoped CLI. Can Factory (Go control plane) drive it headlessly: `--no-input`, `--json` surfaces, `devvm ls/stop/rm/adopt/host`, exit codes, and identifying a VM by folder vs path. What is the stable automation surface, and what is interactive-only today? Is there an API, or is CLI-wrapping the only path? Startup cost per VM, and whether a VM can be created for an ephemeral task directory.
2. **One VM per thread.** Factory's unit is a Task/Run executing a workflow process. What's the real lifecycle semantics of devvm VMs (create on first use, stop, rm, restart, adopt, own clone with `--clone`, git protection, ports, SSH host)? Is per-task VM creation practical (startup seconds, disk duplication, warm pools), or is per-project VM reuse the honest default? What do groups/links between VMs buy for multi-agent waves?
3. **Secrets per project.** devvm's documented model: secrets are saved on the machine (`devvm secret set github`), a VM is bound with `devvm secret use`, and the VM gets a **placeholder** while the proxy injects the real value into requests for that secret's hosts. Verify this precisely from the source/docs: which secret classes exist (github, claude, proxy, others?), how binding is scoped, what the VM actually sees, which protocols the proxy covers (HTTPS only? git over SSH? `gh` CLI? model API calls?), failure modes when a placeholder leaks into a request, and whether a per-project secret set can be enforced without giving every VM all machine secrets. Does this strengthen or complicate ticket 009's capability profiles (which must express "this role may use these secrets for these hosts")?
4. **Network, egress, and audit.** Confirm the network tiers (`open`/`internet`/`allowlist`/`none`/`unenforced`), the allowlist proxy, `devvm network log`, and what audit evidence it emits. How would Factory compose this with its own append-only measurement log (directive #15): is devvm's log queryable/exportable, or only human-readable?
5. **Fit and risk.** Platform support (Linux: Lima? KVM? containers?), kernel of the VM, resource overhead per VM (memory/disk/CPU settings), concurrency limits, licence/source availability (github devvmhq/devvm), vendor lock-in, and the security claims versus the known pattern (placeholder + egress proxy + VM kernel boundary). Compare devvm honestly with the general 2026 consensus (microVM/gVisor + credential broker + allowlist egress) and with the cheaper alternative of Factory-owned worktrees + OpenCode permissions (which 002 already said are not a sandbox).

Verdict must state: adopt/adapt/avoid for devvm as Factory's sandbox layer; the honest isolation granularity (per task vs per project); the per-project secret-binding design; which map tickets (006 adapter, 009 capability control, 010 daemon, closed/004 observability, fog "where agents run"/deploy) are touched and whether any reshape; and what Factory would measure (VM startup, secrets denials by host, egress blocks, task isolation failures). Date claims 2026-11-18; devvm.dev docs and the devvm source are primary, the local CLI is evidence.

## Resolution

All claims dated **2026-11-18**. Evidence: devvm.dev docs (last updated 2026-11-05/06), the source `github.com/devvmhq/devvm` at `main` 8afdec7, `VERSION` 0.1.1-rc.3 (756 commits, active today), and the locally installed binary 0.1.0 (mise) — the installed binary **predates** several findings below (custom secrets, the 17-VM cap, the split proxy); its `--help` output is the 0.1.0 surface.

### 1. Programmatic lifecycle — CLI-wrapping is the only surface, and it is a good one

- **No API, daemon, or SDK.** The automation surface is the CLI only. There is no devvm server to talk to; devvm spawns per-run helper processes (proxies, forwarders) and exits when the shell does. Factory wraps the CLI — which closed/006's control-plane shape already assumes.
- **Headless support is explicit and designed:** `--no-input` ("never ask, and fail where devvm would ask, naming the flag that answers it"), a documented questions table where *every* interactive question has a flag/command that answers it, and `--json` on every show/list command ("output for scripts"). The JSON contract is versioned (`"version": 1`) and **additive-only**: shapes only gain fields; renames/type changes bump the version (docs, *The command line*, 2026-11-06). This is a genuinely stable automation contract.
- **Folder-scoped commands.** Most commands act on "this folder's VM", resolved by the working directory plus the folder's identity (path + device + inode + birth time — a rebuilt folder never inherits the old VM). `devvm ls --json` is global (verified locally: `{"version":1,"vms":[]}`); `devvm adopt VM` and `devvm rm VM` accept a VM name; `devvm stop/rm/restart/network/secret use` are folder-scoped — Factory must `chdir` into the task's directory to drive them, or use `adopt`.
- **Gaps for Factory:** exit codes are not a documented contract (refusals are descriptive messages; only "usage error" is named). No `devvm exec`/`--run` — the bare `devvm` opens a shell that "reads its commands from devvm's input" without a terminal; the practical headless path is `devvm host --no-input` then plain `ssh <vm-name>`, which devvm makes safe (pinned per-start host keys, agent/tunnel forwarding off, own ssh config entries). Deletions refuse without `--force` where no terminal exists — correct for automation.
- **Ephemeral task directories work.** A VM can be created for any fresh directory (fresh inode ⇒ new VM identity), including one Factory makes per Run. Caveat: some file systems are refused for folder-identity matching (FUSE/network/overlayfs never match), and on Linux QEMU mounts the folder **by path** (no `/.vol` device-inode mount like macOS), so a nested-folder swap has a small documented race on Linux.
- **Cost:** first base image build "in a few minutes"; "later VMs start in seconds" (README). On Linux each VM disk is a **qcow2 overlay of the image's disk** — creation is cheap and shares image blocks (`du` overcounts); images are read-only once built and can't be deleted while overlays use them. A warm pool is unnecessary; a pre-built Factory image (base + toolchains + agents as a devvm layer/image) is the warm state.

### 2. Isolation granularity — per-Managed-Project VM reuse is the honest default; per-Run VMs are an escalation, not the base

- **devvm's own model is one VM per project folder**, not per process/thread. Lifecycle: create on first use; `stop` (checks `.git`, names Linux set-id files, removes the ssh entry); `rm` (exports agent history first, checks `--clone` VMs for unfetched commits, deletes state/allowlists/logs/CA); `restart`; `adopt` for re-created folders; remake via `layer add/rm`, `update`, `clone on/off` (transactional with undo). `--clone` gives the VM its own repo clone (untracked files, credential helpers, `.git` stay host-side; work returns only when Factory/host fetches `devvm/<branch>`; full repo copy incl. branches, stash, staged files in 0.1.1-rc).
- **A hard concurrency ceiling exists: at most 17 VMs at once** (breaking change on `main`, Unreleased, 2026-11-18) — each VM's ssh occupies one of 17 browser-refused ports. A 17-VM cap makes "one VM per agent session in every wave" impossible on a busy machine, and each VM is a full Linux VM with `--cpus/--memory/--disk` (defaults from `devvm size -g` or the image) — memory, not CPU, is what binds waves.
- **Groups/links do not buy wave isolation.** A `group` links every member to every other's published ports — it explicitly **joins the trust of all its VMs** ("put VMs in one only when you'd trust each with what the others have"); a link connects a client only to targets on its own tier or stricter, to ports the target publishes on its loopback. They are service-composition primitives (a db VM behind an app VM), not a multi-tenant boundary. Verdict: do **not** use groups/links to model Waves; Waves stay Factory-level dispatch (008) sharing one Task's VM.
- **Honest granularity:** **one devvm VM per Managed Project, reused across Tasks, is the default** — matching devvm's design, the 17-VM cap, and agent-history/toolchain reuse. **One VM per Task/Run is practical as an escalation** (Factory creates a per-Run directory under its run root; VM starts in seconds on an overlay disk; `rm` after merge) and is justified for untrusted code, self-hosting Factory, or competing Tasks on the same project. Inside a VM, agents of a Wave share disk, bindings and tier — per-agent isolation within a Task must come from OpenCode permissions (009), not devvm. `--clone` per Task VM keeps the host working tree clean and is the recommended pairing for per-Run VMs.

### 3. The secret model, precisely — placeholders + per-VM binding + scoped injection, and it does support per-project secret sets

Verified against the current docs and source (`internal/secrets/custom.go`, `docs/content/docs/safety/network.md`):

- **Where values live:** macOS Keychain, or `~/.local/share/devvm/secrets/<name>` — a file only the user can read. No devvm command prints a value; each VM's proxy reads what it needs itself. Values are validated on save (no quotes/backslash/control chars, no placeholder values, ≤3800 printable-ASCII chars).
- **Secret classes:** three **known** secrets — `claude` → `api.anthropic.com`, `Authorization` (auto-bound for every VM whose image has `claude`); `github` → `api.github.com`, `github.com`, `codeload.github.com`, `raw.githubusercontent.com`, `Authorization` (Bearer/token, and git's Basic `x-access-token:PLACEHOLDER`); `proxy` → the company-proxy password, which **no VM ever gets**. Plus **agents' logins** (Claude Code, Codex, opencode, Cursor CLI in rc): devvm's agent store keeps one login per agent; the VM gets placeholders, devvm refreshes OAuth on the host so a VM never holds a refresh token. Plus — **added after 0.1.0, in current main/docs — "secrets of your own":** `devvm secret set NAME --host HOST [--env V] [--header H] [--prefix P] [--path /api/] [--method GET,HEAD] [--scheme S] [--basic-user]` — arbitrary API keys (Stripe, OpenRouter, company services) with up to 16 exact hosts (wildcards refused), a required env var the VM sees its placeholder in, header-shape restrictions (Host/Cookie/X-Forwarded-*/etc. refused), and **method+path scoping** (a `GET,HEAD`-only key: a POST carries only the placeholder, which the host refuses).
- **Binding scope:** per-VM, via `devvm secret use NAME` run in the VM's folder (machine-global secret names; binding is the per-project axis). A bound secret's hosts **join that VM's allowlist on port 443** even on the `none` tier. `unuse`/`rm` take effect immediately — the VM only ever held the placeholder.
- **What the VM sees:** the placeholder in `CLAUDE_CODE_OAUTH_TOKEN`, `GH_TOKEN`, a git credential helper for `https://github.com`, or the custom secret's `--env` variable. Placeholders carry a random per-VM suffix, so a placeholder copied out of the VM is worthless elsewhere; the proxy authenticates each VM (VM-only CA) and requires the VM's own password, so neither another VM nor a host program can spend a secret through a proxy.
- **Protocol coverage:** everything that transits the VM's proxy — intercepted HTTPS tunnels (TLS re-terminated via the VM-only CA) and plain HTTP forwards. That covers **model API calls** (Claude Code and any SDK reading env/header vars), **`gh` CLI** (`GH_TOKEN`), **git over HTTPS** (credential helper), and custom-header APIs. **Not covered:** git over SSH (no secret injection; the SSH agent path is the alternative, and main's agent relay lets VMs list/sign but not remove/lock/add keys), raw TCP to arbitrary ports, and tools that bypass the proxy (below).
- **Failure modes:** (a) a tool that ignores `HTTP(S)_PROXY` fails outright on confined tiers (DNS/connection error — names resolve in the proxy) or, on `open`, connects directly carrying only the placeholder, which the host refuses; (b) a placeholder in a shape the proxy doesn't inject (wrong scheme, double placeholder, non-listed method/path) **stays a placeholder** and the server rejects it — fail-closed, and the proxy logs why without the value; (c) CA expiry after 30 days without a launch blocks secret-host requests with reason `devvm's CA has ended`; (d) **minting**: the proxy refuses GitHub REST calls that create SSH/deploy keys, self-hosted runners or webhooks (refused even if allowlisted), but cannot stop GraphQL/OAuth-app grants — rotate after distrust; (e) a fine-grained GitHub token scoped to the project's repos is the documented mitigation for the worm case (Shai-Hulud).
- **Per-project sets without giving every VM all machine secrets: yes.** A VM sees exactly the secrets bound to it (plus its agents' logins and `claude` if its image has the agent). Per-project design: name secrets per project or per project+role (`stripe`, `github-acme`), keep them fine-grained, bind only to that project's VMs, and deny writes where read-only is intended (`devvm network deny api.github.com --method POST,PUT,PATCH,DELETE`).
- **Ticket 009 impact — strengthens it.** Capability profiles can now express "this role may use these secrets for these hosts" as **sandbox-enforced claims** (tier + allowlist + secret bindings), which devvm enforces at the network boundary — stronger than OpenCode's in-agent permission prompts (which 002/015 showed are advisory under arbitrary child processes). The division of labor for 009: devvm enforces the **per-VM ceiling** (network tier, allowlist, secret set), OpenCode permissions refine **within** a VM (per-agent tool policy, always-ask); secrets can't be split per agent within one VM, so per-role secret granularity is bounded by the VM granularity chosen in §2.

### 4. Network tiers and audit — four tiers, structured logs, and a real composition path for directive #15

- **Tiers confirmed:** `open` (unconfined — everything the host reaches, incl. `localhost` and LAN; the one tier not confined to its proxy), `internet` (all public hosts, minus denies), `allowlist` (default for new VMs; built-in policies for OS packages/toolchains/layers + user files, deny beats allow), `none` (only its agents' and secrets' hosts and links), plus the **status** `unenforced` (a confined tier not in force — devvm's self-check stops or offers-restart such VMs on every launch). Confinement is outside the VM: on Linux, QEMU runs behind a devvm wrapper with `restrict=on` and a single `guestfwd` to the proxy — even root cannot dial out; DNS resolves only in the proxy (no DNS-tunnel channel); internal/loopback/link-local/CGNAT addresses refused unless a rule names them.
- **Rules are fine-grained:** host/wildcard/`**`/CIDR, ports (`RULE:22`), and — new since 0.1.0 — **method and path** qualifiers on allows and denies. Per-VM policy files live outside the VM's reach; broken deny lines fail closed (everything denied until fixed); a changed-but-unreadable file keeps its last rules so a deny never lapses.
- **Audit evidence:** `devvm network log` per VM (human lines: time, allowed/BLOCKED/cache, host:port, the allowing rule, the request, `, token: github`) and **`devvm network log --json`**: one versioned object of events — `tunnel`/`intercept`/`forward`/`blocked`/`nix-cache` — each with `time, host, port`, and where applicable `method`, `path`, the `rule` that allowed it, the block `reason`, the `User-Agent`, the `secrets` put in, `refused` (refused regardless of allowlist — the credential-minting guard), the company-proxy `upstream`, and a link's `target`. `--blocked` gives a per-host summary with the exact `devvm network allow` command. Retention: rolling ~10 MiB + one older file per VM; **`devvm rm` deletes the VM's logs** — a durable-audit system must ingest them, not rely on them. In-VM mirrors: `http://devvm.proxy/blocked`, `devvm-why`.
- **Composition with the measurement log:** Factory polls `network log --json` per Run (or tails `--follow` in its daemon) and normalizes into closed/004's event envelope as `network_request` events (`operation: http_request`, `target.host`, `outcome: succeeded|denied`, `details: {rule, secrets, reason}`) — **enforcement-level coverage that closes closed/004's "filesystem/network by arbitrary child processes = partial/unobserved" gap on the network axis**. Content-free by design: host, method, path, rule — no query strings, headers, or bodies. Files on disk under `~/.local/share/devvm/vms/<hash>/` are the raw fallback.

### 5. Fit and risk — Linux support is real; MIT source; claims match the 2026 consensus with honest gaps

- **Platform:** Lima is the only backend. macOS 13+ (Virtualization.framework) or **Linux with QEMU + `/dev/kvm` access**, arm64 and x86_64; not Intel Macs yet. Each VM is a **full Linux VM with its own kernel** (Ubuntu cloud image, or any container image via `--from` whose kernel boots) — a true kernel boundary, not containers. (This machine is Linux/x86_64 with KVM — compatible.)
- **Overhead and limits:** per-VM CPU/memory/disk via `devvm size`; **17 concurrent VMs** (rc limit); proxy per VM caps ~1024 tunnels (2048 connections of all kinds on main); port forwarder ≤256 ports/VM; links ≤256 connections. Builds on Linux: only no-network builds are fully confined (QEMU can't drop host loopback while keeping internet).
- **Linux-host caveats (honest, documented):** **no `.git` protection on Linux** (no immutable file flags) — the VM can write `.git/hooks`/`config` that host git would run; devvm's own git commands disarm repos it reads, and the documented mitigation is `--clone` (which Factory would use anyway for per-Run VMs). **Set-id bits propagate from VM writes on Linux** (devvm scans and names them on stop/make). The proxy's child self-confines with **Landlock + seccomp on Linux** (main), and refuses every direct connection (all connects go through the parent proxy process).
- **Licence/source:** MIT (`LICENSE` in repo and local install, © 2026 w3cj); public Go repo, 756 commits, 702 stars, 36 forks, releases signed with a minisign key, SECURITY.md, active issue tracker. Lock-in is **procedural, not legal**: MIT makes a fork possible; the real coupling is the CLI-as-API (a Factory adapter), the per-folder state model, and Lima. `devvm limactl` even exposes Lima directly for debugging (unconfined — an escape hatch, flagged as such). Risk profile: young project (0.1.x, first release ~Nov 2026), single maintainer-ish, breaking changes on main (17-VM cap) — Factory's spec should pin a version and treat the JSON `version` field as the contract.
- **vs the 2026 consensus** (microVM/gVisor + credential broker + allowlist egress): devvm **is** that pattern — VM kernel boundary (stronger isolation than gVisor's shared-kernel model, at higher cost), a host-side credential broker that never gives values to the sandbox (placeholders + scoped header injection), and a default-allowlist egress proxy with denies, method/path rules, and structured audit. Differences: no in-VM syscall filtering (unneeded given the VM boundary); secrets are per-VM, not per-process; no remote/fleet story (single-host by design). It is honest about its gaps (a dedicated attack-vectors page with "Blocked / Kept inside the VM / Narrowed, not closed / Left to you").
- **vs Factory worktrees + OpenCode permissions:** not alternatives — complementary layers. Worktrees separate *workspaces* (002/006 settled: not sandboxes); OpenCode permissions constrain the agent's tool calls but not arbitrary child processes. devvm closes what both leave open: network exfiltration, credential theft (nothing of the host's is mounted), and host mutation (`--clone`), with enforcement outside the agent's control. OpenCode runs *inside* the devvm VM as the RuntimeAdapter.

### Verdict

**Adapt** devvm as Factory's sandboxing and secret layer — adopt the substrate, adapt the granularity and the secret naming, and keep the CLI wrapper behind Factory's own adapter so the substrate stays replaceable.

1. **Isolation granularity (honest):** one devvm VM **per Managed Project**, reused across Tasks, is the default; **one VM per Task/Run** (in a Factory-created per-Run directory, with `--clone`) is the escalation for untrusted code, concurrent conflicting Tasks, or Factory self-hosting — gated by the 17-concurrent-VM cap and per-VM memory. **Waves share their Task's VM**; per-agent isolation inside a VM is OpenCode's job (009). Groups/links are service-composition tools, **not** wave boundaries.
2. **Per-project secret-binding design:** Factory stores, per Managed Project in its Workflow Artifact, a declarative **secret-bind profile**: secret name(s) (fine-grained, per-project where tokens permit), hosts, header/env, and method/path scope — applied as `devvm secret set NAME --host … --env … [--method …]` once on the machine and `devvm secret use NAME` in each VM's folder at Task start; the profile's hosts double as the VM's allowlist additions. Values are entered by the Owner (`--stdin`), live in the OS keychain/devvm's store, and never appear in the Workflow Artifact, in VMs, or in logs. Capabilities a profile grants are enforced by the sandbox, not by prompts.
3. **Ticket impacts — one reshape, several refinements:**
   - **009 (capability control):** profiles gain a **sandbox axis** — network tier, egress rules, secret bindings — enforced by devvm outside the agent; OpenCode permissions remain the in-VM refinement and always-ask stays agent-level. This *strengthens* 009's "profiles + always-ask for high-risk" lean: the sandbox makes high-risk categories structurally unreachable rather than merely gated.
   - **006 (harness substrate):** refines, does not re-open. devvm is Factory-owned **infrastructure below the RuntimeAdapter**, not a second adapter: the capability descriptor gains sandbox claims (`sandboxed_network: tiers`, `secret_binding: per-vm`), and Factory-managed OpenCode servers run inside VMs. The adapter contract is untouched.
   - **010 (daemon vs CLI):** the resident-model argument **strengthens** — devvm already runs resident per-VM proxies/forwarders, and Factory needs a resident process to ingest `network log --json` per Run, apply tier/bind profiles at Task start, and enforce retention (devvm deletes logs with `rm`). Both consumer models remain sketchable; devvm neither settles nor blocks 010.
   - **closed/004 (observability):** strengthened, no re-open. `network log --json` normalizes into the event envelope as enforcement-level `network_request` events — the network axis of 004's "partial/unobserved" coverage warning closes for sandboxed runs; file and shell axes keep their 004 caveats. Retention rule adopted: ingest into Factory's log, don't trust devvm's rolling files.
   - **Fog "where agents run" — resolves for the local machine:** sandboxing = devvm VMs per the granularity above; worktrees remain workspace separation inside/beside VMs; **deploy fog untouched** — devvm is single-host and says nothing about multi-machine SSH deploys.
4. **What Factory measures (directive #15):** VM **start time** p50/p95 per Run (cold vs image-cached); **image/toolchain build** time and refresh frequency; **secret denials by host** — requests that left with a placeholder and were refused (proxy `refused`/placeholder-shaped events), i.e. a role tried to use a secret it wasn't bound; **egress blocks** — count/rate of `blocked` events per VM, per host, per reason, and `--blocked` `ALLOW WITH` suggestions (proxy of workflow friction); **tier violations** — `unenforced` sightings and self-check stops; **task isolation failures** — VMs stopped by the self-check, folder-identity refusals, set-id files named, cross-Task port contention; **resource** — concurrent VM count vs the 17 cap, per-VM memory/disk, overlay disk growth; **link/group refusals** (`link_refused`, tier-downgrade refusals) if links are ever used.

## Owner decision (2026-11-18)

**One devvm per Managed Project.** The sandbox boundary equals the project: the project's runtime server and every agent session for that project (across concurrent Tasks and waves) run inside its single VM; its secret bindings and network tier are the project's configured set. Consequences the spec must carry:

- Capability profiles (ticket 009) are the *within-VM* control — devvm enforces the project ceiling (VM lifetime, network tier, secret bindings); profiles decide what a role may touch inside it.
- Per-Run VM isolation remains an escalation option (untrusted input, destructive tasks), not a default; the 17-VM cap is therefore not a v1 constraint.
- The Factory-managed runtime server for a project (ticket 006) lives inside that project's VM; the Go control plane stays on the host and reaches it via `devvm host` + SSH.
- Secrets are project-scoped by construction: binding a secret to the project's VM grants it to every role in that project unless profiles withhold it.

Glossary term: **Project VM** (added to `CONTEXT.md`).

**Superseded in part (2026-11-20, ADR-0009).** Item 2's secret-bind profile is not stored in the Workflow Artifact: the artifact names secrets only, while hosts, header/env, method/path scopes, and values are local devvm config. Item 1's one-VM-per-project decision stands.
