## Question

Swamp Club ([site](https://swamp-club.com/), [source](https://git.swamp-club.com/swamp-club/swamp/src/branch/main), manual at swamp-club.com/manual) argues AI systems should be built from **repeatable behaviors** — deterministic, named, reusable operations composed into workflows — rather than token-hungry agent-centric designs. This overlaps Factory's ambition almost point for point and may change Factory's design. Study it deeply and extract what Factory should adopt, adapt, or avoid:

1. **The behavior model**: what a "behavior" actually is — its definition format, typing (they show zod schemas), invocation surfaces (harness tool, CLI, Slack, API, webhook), and how behaviors compose into workflows. Compare directly with closed/011's decided **typed workflow graph + CEL guards in Go** — same idea? Where does their authoring/ergonomics beat or lose to that shape?
2. **Extensions registry** (1,850+ behaviors incl. `@swamp/software-factory` — study that one especially, it is a prior art close to Factory itself): packaging, versioning, distribution, trust model. What does a mature behavior ecosystem teach Factory about its (still fogged) path-to-other-users and reusable workflow-like primitives?
3. **The seams with any harness** (Claude Code, OpenCode, Pi…): how they inject behaviors as tools into arbitrary harnesses. Does this strengthen or threaten the hybrid substrate decision space around ticket 006 (Factory could itself be a Swamp behavior pack vs a Swamp competitor)?
4. **Platform mechanics**: secret vaults, structured datastore with lifetimes/query, OTel/SIEM observability, `swamp serve` with grants & groups, remote workers/fleet (build-7f3a…), scale-out story. Which of these map onto Factory's open decisions (009 capability control, 010 daemon-vs-CLI, deploy pipeline fog) — and confirm against primary docs, not marketing copy.
5. **License, self-hosting, and independence**: source availability and license terms at git.swamp-club.com, extension registry terms, and what "building on Swamp" would cost Factory in dependence vs learning-for-free.

Verdict must state: per-concept adopt/adapt/avoid recommendations with reasons, which map tickets the findings touch, and whether any open decision (006, 009, 010) or recent closure (011) has reason to re-open or reshape. Date claims 2026-10-27; prefer primary docs, the repo, and third-party field reports (reset.dev, dieter.plaetinck.be, mcginniscommawill.com, stack72.dev) over the homepage's marketing.

## Resolution

**Research snapshot: 2026-10-27.** Three parallel primary-source passes: the full manual (swamp-club.com/manual, 37 pages), shallow clones of `swamp-club/swamp` (HEAD `602abe64`, 2026-10-27) and `swamp-club/swamp-extensions` (HEAD `1df2c88`, 2026-10-27), and all six designated field reports (every URL resolved, no 404s). Two verdict-critical claims were re-verified first-hand: the account-requirement page and the Software License Agreement (both fetched directly, 2026-10-27).

**Headline.** Swamp independently converged on closed/011's shape — a typed, declarative workflow DAG interpreted by an engine, with CEL for guards and data wiring — and adds three things Factory has not yet decided: an agent-authorable YAML+JSON-Schema frontend over that graph, a grant-based capability model, and a harness-neutral skills+CLI seam. It also carries two hard dependencies Factory must not inherit: AGPLv3-with-exception licensing sitting on top of closed hosted services, and a **mandatory swamp-club.com account for every command, including fully-local repositories**.

### 1. The behavior model, point-by-point against closed/011

**What a behavior is.** Two halves (glossary, verbatim): "a type (reusable TypeScript logic) and a definition (YAML configuration). The type defines methods and schemas; the definition fills in the specifics for one use." The type is TypeScript exported from an extension (`extensions/…` file declaring a `behavior` object) with **zod@4** schemas for `globalArguments` and per-method `arguments`, an `execute(args, context)` per method, CalVer `YYYY.MM.DD.MICRO` versioning, and an explicit `upgrades` chain. The definition is YAML at `models/<type>/<name>.yaml` whose `inputs` block is JSON-Schema-shaped; values may embed `${{ CEL }}` expressions. Definitions are "data, not code — an agent produces them by writing YAML that conforms to the type's schema." (Terminology note: "behavior" renamed from "model" in a recent release; `swamp model` and step type `model_method` still work.)

**Invocation surfaces (confirmed).** CLI `swamp behavior run` — "the single most important command in Swamp" — plus workflow steps, cron triggers, HMAC-verified webhooks (`github|linear|stripe|slack|jira|generic` + extension schemes), a WebSocket API on `swamp serve` (`--server/--token` on every command), behavior-to-behavior `context.runModel()` (depth cap 10, 100-invocation ceiling), and approval commands. **Not found:** Slack as an invocation surface (Slack exists only as a webhook signature scheme), any REST endpoint that executes behaviors (REST is health/cancel only), and **any MCP server** — the repo states it deliberately: "It runs no MCP server, never calls an LLM API… Agents drive swamp; swamp does not host one."

**Workflows.** YAML DAG of jobs → steps in `workflows/workflow-<uuid>.yaml`; "Steps declare their dependencies; the engine resolves topological order and runs independent steps concurrently" (Kahn's algorithm with `weight` tie-breaking, cycle detection with path). Step task types: `model_method` (behavior), nested `workflow`, `manual_approval`, `assert`, `wait_for_signal`. Conditions `always|succeeded|failed|completed|skipped` composed with `and/or/not`; `allowFailure`; `forEach` over a CEL-resolved collection (concurrent, per-iteration data outputs, `self._index`); a `guard:` CEL expression that skips a step (emitting `step_skipped` with `reason: "guarded"`); `assert` with `low|medium|high` severity and JUnit export. Data flows through **deferred CEL data functions** (`data.latest(...)`, `data.query(...)`) that the engine treats as step-output dependencies and resolves at execution time; a missing value "fails loudly rather than passing through a blank value." **No declarative per-step retry policy exists** — retries are operational: `swamp workflow resume` re-runs failed steps and their downstream in the same run ("A retry does not guarantee exactly-once execution"), and `swamp workflow recover` checkpoints after interruption. A field report found the failure-propagation gap first-hand: "a sequential loop in Swamp keeps going after an iteration fails. I'd assumed it would stop, so I tested it. It doesn't."

**Point-by-point vs closed/011 (typed, declarative graph owned and interpreted by Go; CEL only for guards):**

| Point | closed/011 (decided) | Swamp (observed 2026-10-27) | Assessment |
| --- | --- | --- | --- |
| Representation | Go-owned, versioned typed IR; language-independent | Engine-interpreted YAML DAG (jobs/steps), topologically ordered, validated (cycles, refs, schemas) | **Same idea.** Swamp is production evidence that the 011 shape works; neither threatens the other. |
| Authoring | Dhall frontend gated on `dhall-golang` conformance; JSON IR interim | YAML + `${{ CEL }}` + JSON Schema inputs, written by agents | **Swamp wins ergonomics** (see below). Adapter candidate: a YAML/JSON-Schema frontend over the same Factory IR. |
| Guards | CEL only, side-effect-free | CEL everywhere: guards, conditions, inputs, asserts, grant `--when` conditions (with cost budgets: AST depth ≤ 24, nesting ≤ 2, cost ≤ 500) | **Adopt** the CEL usage vocabulary and the cost-budget discipline for embedded CEL. |
| Typing | Typed step inputs/outputs in the IR | zod@4 on types (code layer); JSON Schema at the definition boundary; schema-validated, versioned data artifacts | **Adapt:** use JSON Schema as the interchange/validation format for IR step I/O; zod stays their implementation detail. |
| Step vocabulary | `Step.run`, bounded `ForEach`, retry policy, approval nodes | `model_method`, nested workflow, `manual_approval`, `assert`, `wait_for_signal`, `forEach`, `guard` | **Adopt** `assert` and `wait_for_signal` into the IR vocabulary; **keep Factory's declared retry** — Swamp's absence of it is a documented gap, not a design. |
| Failure/retry | Typed retry fields on step nodes (engine semantics) | Operational resume/recover only; "not exactly-once" | 011's declared-retry choice is vindicated; **borrow** the checkpointed `recover`/`--from <step>` UX (skip completed steps to protect irreversible side effects). |
| Effects | Go interpreter owns runtime effects; no user effects in the language | Same split, but their "code" layer is TypeScript `execute()` running **in-process in Deno** with scoped permissions (`--allow-read/write/env/run/sys/net`; no `--allow-all`/FFI) | **Adapt:** keep 011's plan — user code behind the versioned subprocess/WASM worker, never in the engine process. Their code/data split (types = code, definitions = data) is the principle Factory already holds. |
| Composition | Functions/imports generate finite graphs | Nested workflows + `context.runModel()` with hard caps (depth 10, 100 invocations) | **Adopt** the invocation caps for any behavior-to-behavior calls. |
| Approvals | Approval nodes | `manual_approval` suspends run (`suspended`/`waiting_approval`); approve ≠ resume; approver needs the `approve` grant; auto-resume matrix | **Adopt** the approve/resume separation and grant-gated approval. Field report caveat: one author moved gates to GitHub labels because he "don't want a long-lived suspended run sitting around" — approval UX needs a timeout story. |
| Discovery/ergonomics | (open — successor ergonomics ticket) | `behavior type describe --json` (full JSON Schema), `--compact` agent digests, `behavior search --json`, `behavior validate` (6-point checklist), `--input/--stdin/--tag/--skip-check` | **Adopt as the benchmark.** This machine-readable discovery surface is what makes the model agent-usable; the Factory ergonomics ticket must beat it. |

**Ergonomics verdict for Q1.** Swamp's authoring wins where it matters most for Factory: an agent reads a schema, fills YAML, runs `swamp validate`, executes — no plugin SDK, no compile step, proven at ecosystem scale (1,914 extensions). It loses on: dense docs (independent reviewer), metadata extraction that fights the formatter (see §2), no declarative retry, surprising fail-continue loop semantics, and a primitive layer (TypeScript-in-Deno) that is code execution in the engine process rather than the typed functional workflow code the owner required. **The 011 decision stands**; what Swamp adds is a concrete candidate for the successor ergonomics ticket: a **YAML + JSON-Schema frontend over the same IR**, with Dhall no longer the only frontend worth prototyping.

### 2. The extensions registry, trust model, and `@swamp/software-factory`

**Packaging/versioning/distribution.** One `manifest.yaml` per extension: `manifestVersion`, scoped name `@collective/name` (`@swamp`/`@si` reserved), CalVer `YYYY.MM.DD.MICRO`, SPDX `license` (required by registry terms), content lists (`models`/`workflows`/`reports`/`skills`/`vaults`/… — the manual and in-repo design docs use both `models:` and `behaviors:` spellings after the rename), dependencies, platforms, labels; release channels `stable|rc|beta`; `swamp extension push` (CI auto-publish on version bump), `pull/install/update/yank/deprecate/promote`. Installs land in `.swamp/pulled-extensions/` **pinned in a committed lockfile** (`upstream_extensions.json`) with SHA-256 checksums verified on pull; unknown types from trusted collectives auto-resolve from the registry on first use. Counts (checked on the registry browse, 2026-10-27): **1,914 extensions, 1,702 exposing behaviors** (the homepage's "1,850" is a marketing counter of behaviors; cite 1,914/1,702).

**Trust model (verbatim where it matters).** "A registry is a distribution mechanism, not a quality guarantee — it tells you an extension exists, not whether it is safe to run." Defaults: only the first-party `@swamp` collective is trusted and cannot be removed; "Membership collectives are not trusted automatically… A compromised or careless member's publish must not be able to run code in every repo"; even trusted collectives are lockfile-pinned ("a trusted collective still cannot silently push an updated version"). Integrity = SHA-256 checksums; **content signing is documented as future work** (swamp-club#3972), legacy unsigned archives still allowed. Sandboxing is explicitly *not* sandboxing: a push-time hygiene gate ("The check is a hygiene gate, not a sandbox") blocks `eval`/`Function`/hidden files/symlinks/size limits, plus a dependency-trust audit (OSV, license allowlist) and a quality rubric; runtime is Deno's per-CLI scoped permissions. Two review layers: a static "mechanically-decidable floor" (critical/high block push) and an AI adversarial review pass. The curated "Verified" badge is separate from the automated score: "Most extensions do not carry this badge, and that is expected." Registry terms (v20261012): submitter-declared licenses, "AS IS", no warranty, **aggregate liability capped at $100**, removal at sole discretion, California law.

**The ecosystem's cautionary tale** (field report, hands-on): the registry never runs your extension — "It reads your source as text" via a regex zod scanner (`parseZodObjectFields`), so formatter-friendly code silently disappears from the catalog: an extension graded **A at 100% with 38 of 258 arguments listed**, shared shapes (`...ItemRefShape`) invisible, single-line field requirement forcing copy-paste "the opposite of what a reviewer asks you to do." **Lesson for Factory: any catalog/registry/discovery metadata must be derived from the typed schema itself, never scraped from source text** — and quality grades must be shown next to what they actually measured.

**`@swamp/software-factory` in depth (Q2's special subject).** Registry page + source (`swamp-extensions/software-factory/`): v2026.10.23.1, `AGPL-3.0-or-later`, first-party, grade A 93/100, **210,208 downloads** (3rd most-used extension), no verified badge, five versions since June 2026. It is "**a fully generic, model-driven state machine** for guiding agents through a software development lifecycle. The entire machine — stages, transitions, gates, required artifacts, review skills, agent commands, system prompts — lives in the model definition's globalArguments as data. The engine ships no lifecycle concepts." One behavior type, 13 methods: `start`, `status` ("The driver's entrypoint"), `record_dispatch` (proves a stage ran; third dispatch of an entry fails as runaway-loop), `record_artifact`, `record_evidence`, `resolve_findings`, `approve`/`reject` (human gates), `advance`, `summary`, `validate`, `describe` (Mermaid render), `reset`. Versioned per-work-item resources: `state`, `artifact`, `evidence`, `approval`, `validation`, `journal` (append-only), `status`. Nine gate kinds incl. `human-approval`, `max-cycles` (default 5, then park for human `cycle-override`), `cel`, and `workflow-succeeded` ("verified against swamp's own workflow run records, not driver attestation"). Stage work modes: `interactive` (the driving agent), `dispatch` (one subagent per listed skill, spawned by the agent), `workflow` (zero-LLM swamp workflow), `method` (single behavior call — also how trackers integrate). Four shipped example factories: `minimal`, `feature-factory` (plan → adversarial plan review → implement → verified test workflow → adversarial code review → done), `sdlc-classic`, `retry-feedback`. **No built-in lifecycle, no forge/tracker coupling**: "The engine never talks to external systems"; `workItem` is an opaque ref (`ISSUE-42`); integration happens through evidence records and other behavior types. The bundled `software-factory` skill teaches the drive loop ("`status` is the contract… Resume with `status`, never `start`").

**What it means for Factory.** This is the issue-driven loop built as a Swamp behavior — direct proof that (a) a lifecycle state machine with gates, approvals, artifacts, and agent dispatch is expressible as data on someone else's platform, and (b) Swamp's own repo dogfoods the same idea (`verification/workflow-verify-{build,reviews,skills}.yaml` + attestation + auto-merge gates — prior art for Factory's milestone 1 and its self-hosting loop). It also marks the ceiling: **the engine exerts zero control over the driving agent** — no capability control, no session/tool enforcement, no tracker/PR integration of its own, no multi-project scope; the agent still runs arbitrary shell and "posts nowhere itself." Derivatives already exist (`@mgreten/software-factory`, `@adam/software-factory`, `@atalanta/meta-factory`).

**Ecosystem lessons for Factory's fogged path-to-other-users:** ship packaging as one manifest + CalVer + lockfile + checksums (git-first; a public registry is closed infra and can wait); make trust explicit, scoped, and default-deny; expose machine-readable discovery (`describe --json`, compact digests) as the primary API because agents, not humans, are the consumers; derive all metadata from schemas; separate "quality score" from "someone vouched for this." Reusable workflow-like primitives map to extensions' `workflows:` + `reports:` content kinds — Factory's equivalent is versioned workflow packs with declared inputs, which the IR already supports.

### 3. Harness-neutral injection and ticket 006's substrate space

**The mechanism (Q3): three layers, no plugin SDK.** "An agent interacts with Swamp through three complementary layers: instruction files, skills, and the CLI." (1) Per-harness instruction files written by `swamp repo init --tool …` — Claude Code `CLAUDE.md`/`.claude/rules/swamp.md`, Codex/`OpenCode` `AGENTS.md`, Cursor `.cursor/rules/swamp.mdc` — with managed/owned sections. (2) Markdown skills (frontmatter + progressive disclosure, gateway `swamp` skill + `swamp-getting-started`) installed to harness-native dirs: `~/.claude/skills/`, `~/.agents/skills/` (OpenCode), `.pi/…` (Pi); "no executable code, no tool-specific APIs, no plugin interfaces." (3) The CLI as the single execution surface. **Nine built-in harnesses**: Amp, Claude Code, Codex, OpenCode, Copilot, Kiro, Cursor, Pi, AntiGravity — plus a custom-tool wizard (`.swamp-custom-tools.yaml` naming instructions file/mode/skills dir) for anything else. Per-harness **audit hooks** are part of the seam: OpenCode gets `.opencode/plugins/swamp-audit.ts` (tracks command usage), Pi gets `.pi/extensions/swamp-audit.ts` recording `tool_call`/`tool_result` into `.swamp/audit/commands-YYYY-MM-DD.jsonl`. Claude Code also has a marketplace plugin (`swamp@swamp-club`). Field reports corroborate the seam works ("It holds your hand from start to finish") with two named costs: skill context loading ("Swamp needs to teach the agent how to select the data it needs by loading a skill into the context") and dense docs. Evidence is Claude Code/Codex-heavy; **no field report mentions OpenCode or Pi** — their support is documented but not third-party-proven.

**Implication for 006.** This *strengthens* the decision space by adding a candidate that neither 002 nor 005 named: the **harness-neutral orchestrator** (CLI + skills + instruction files, any harness drives it) as an alternative to embedding a runtime. Two consequences:

- **"Factory as a Swamp behavior pack" is feasible but only for the loop's state machine** — `@swamp/software-factory` proves milestone 1 could ride Swamp (gates, approvals, artifacts, dispatch all exist), but Factory's differentiators — per-agent capability control, tracker neutrality, SSH deploy, multi-project scope, authoritative audit — are exactly what the pack cannot provide, and the pack inherits the account gate, AGPL, Deno, and the closed registry. Record it as considered; do not adopt it as the core.
- **"Factory as Swamp competitor" is too narrow the other way.** The valuable part of Swamp's seam is the *interop pattern*: skills + instruction files + CLI means Factory can also be driven from Claude Code, Pi, or any future harness without per-harness plugin work, and per-harness audit hooks show how to keep observability when the harness is foreign. Recommendation for 006's grilling: keep the OpenCode-hybrid base (002's decision), and require the spec's interop surface to be **Swamp-shaped (skills + CLI)** so harness choice becomes swappable — which further lowers 002's switching cost.

### 4. Platform mechanics → 009, 010, and the deploy fog

- **Vaults.** Named backends in `vaults/{type}/{id}.yaml`; built-in `local_encryption` (AES-256-GCM, PBKDF2-SHA256 100k iterations, per-secret IV/salt, files 700/600, never leaves the machine); extension backends (`@swamp/aws-sm`, `@swamp/azure-kv`, `@swamp/1password`). Sensitive zod fields (`.meta({ sensitive: true })`) are auto-vaulted and replaced with `vault.get()` references before persistence; `vault.get` is deferred to runtime; secrets reach shell behaviors as env-var sentinels (`${__SWAMP_N}`) so metacharacters stay literal; `auditReads` flag; refresh hooks with stale-value fallback. **Capability narrowing:** a workflow declares a `vaults:` allow-list — "Every vault operation in a run… on a vault not listed is refused, whoever triggered the run."
- **Datastore.** Every method execution/workflow run/audit event produces versioned, immutable artifacts (structured JSON resources validated against schema, or files) under `.swamp/data/`, SHA-256-checksummed, `latest` pointer. **Five lifetimes**: duration string, `ephemeral` (memory-only, 512 MB budget), `infinite`, `job`, `workflow`; GC by count or duration, three-phase `swamp data gc` + orphan `prune`. Query: `swamp data query` with **CEL predicates** over ~30 fields plus `latestRun()/behavior()` functions, `--select` projections, `QUERY_NO_MATCH/QUERY_MULTIPLE_MATCHES` strictness, lazy-loaded `attributes`/`content`. Backends: local `.swamp/`, NFS, S3/GCS extensions; SQLite catalog is "a cache, not a source of truth"; Litestream replication for serve HA. Tags carry provenance (`initiatedBy: user:stack72`).
- **Observability.** OTel is opt-in and no-op by default ("zero overhead"); span hierarchy `swamp.cli → swamp.workflow.run.command → swamp.workflow.run → job → step → model.method`, run secrets redacted before export; per-worker `OTEL_*` config (serve does not propagate). Command audit is automatic ("Every `swamp behavior run`… writes an audit entry with a timestamp, session ID, and the full command string. No configuration required") via per-harness audit hooks; separate vault audit (reads only with `auditReads`); serve audit commands (`audit.timeline/query/subscribe/export/report/alerts`) gated by `admin` on `access:audit`; SQLite run tracker with heartbeat liveness; health endpoint with p50/p95/p99 windows + SSE. **No SIEM integration page exists** — export path is OTLP only. Honest scope note from the docs: "The audit system records commands, not outcomes" — outcomes live in the data artifacts.
- **`swamp serve` (grants & groups).** Single-port server ("WebSocket upgrades, the worker data plane, plain JSON routes and SSE share the listener"); "The server is the single source of truth. It owns the datastore, resolves vault secrets, stores behavior definitions, and manages the policy snapshot. Clients and workers are stateless." **Grant model: default deny, deny wins**, actions `run|read|write|approve|admin`, resource selectors (`workflow:@acme/*`, `vault:…`, `data:*`), CEL `--when` conditions with cost budgets, `grants/*.yaml`, groups for batch assignment. Separation of duties: `run` implies `approve` unless `--approve-requires-explicit-grant`; `--restricted-model-types 'command/shell'` locks dangerous types behind admin — the exact analog of Factory's "always-ask for high-risk." Auth: admin-minted tokens or OAuth 2.0 Device flow (RFC 8628) with collective admission boundary; **TLS + auth mandatory off-loopback ("This is not configurable")**; `--auth-mode none` deprecated; `--admins` materializes `admin on access:*` from config, not the store. HA = shared datastore + heartbeats (30s/90s TTL) + reconciliation, auto-detected; instances never connect to each other. `--remote-only` disables the local executor.
- **Remote workers/fleet.** Workers connect **outbound** to serve (NAT-friendly; "serve never connects to a worker"); stateless ("no credentials, definitions, or persistent data… All vault resolution and data queries proxy back through the orchestrator"); enrollment tokens (single-use, fleets via `--max-enrollments`, auto-naming + `fleet=` label); least-loaded scheduling; placement by `target`/`labels`/`platform`/`affinity`; elastic queueing with `queueTimeout` (default 10 min); concurrency slots, drain via `--max-dispatches`/`--idle-timeout`/SIGTERM; documented limitation "Workers are currently repo-less"; security doc warns "Connecting a worker to an untrusted orchestrator URL grants that URL code execution on the worker machine… the same trust model as a self-hosted CI runner."

**Mapping onto the open decisions:**

- **009 (capability control): reshape with this vocabulary.** Swamp's grants are the strongest single artifact in this research for 009: named profiles ≈ groups of default-deny grants over resources; always-ask ≈ `--approve-requires-explicit-grant` + `--restricted-model-types/commands`; per-workflow overrides ≈ workflow `vaults:` allow-list + expression authorship checks. 009 should test the owner's "profiles + always-ask" against "profiles = named grant bundles, deny-wins, actions × resources × CEL conditions."
- **010 (daemon vs CLI): reshape, not re-open.** Swamp is an existence proof that **both coexist**: the CLI stays primary ("the single most important command") while a resident `swamp serve` buys cron triggers, webhooks, dashboard, HA, and — matching 010's own constraint — *one owner for credentials, datastore, and policy* (clients/workers stateless). Concrete requirements for 010's sketch: single port, mandatory TLS off-loopback, connect-out workers, heartbeat-based liveness, and the daemon-side account-proof refresh loop (hourly checks, in-memory renewal). Neither model wins by evidence; the sketch-both mandate stands.
- **Deploy pipeline fog:** Swamp's workers are *step dispatchers*, not SSH deployers — they do not resolve Factory's SSH-to-owner-machines decision, and Factory's v1 deploy should not adopt the fleet. Borrow later if per-machine executors appear: enrollment tokens, least-loaded placement, queue timeouts, stateless executors. The observability-schema and self-hosting fogs are partially de-fogged by borrowable patterns (command-vs-outcome audit split, data lifetimes, versioned artifacts), but no ticket is opened for them here — main session's call.

### 5. License, self-hosting, and independence cost

- **The code (repo, verbatim):** `AGPL-3.0-only` ("Swamp is licensed under the GNU Affero General Public License, version 3 only") plus a bespoke **"Swamp Extension and Definition Exception" v2.0**: extensions and definitions may be licensed proprietary — but only if they "add functionality to or configure Swamp," "interoperate with unmodified official versions," use only documented APIs, contain no Swamp source, and **"do not include copies of any Swamp source code… This permission does not apply to any extension that exposes so much of Swamp's functionality… that it becomes a practical substitute for Swamp."** Every `.ts` file carries a header-enforced AGPL+exception notice. Separate `TRADEMARKS.md`.
- **The services are closed:** the registry/web backend is not in the repo; `OSS-FAQ.md`: "Swamp is itself a commercial product produced from the open source software, exclusively by Elder Swamp Club, Inc." and self-distributors "may not use any services provided by Elder Swamp Club, Inc. That includes Swamp Club, Extensions, etc." The pricing FAQ's phrasing ("free software under the AGPLv3, but it is distributed under the terms of our software license agreement") sits oddly beside the Software License Agreement (v20261013), whose §3 says Swamp OSS is *not* under that agreement — the SLA governs the proprietary "Licensed Software" and no-fee use (terminable anytime, as-is), defines "Derivative Work" broadly, and (§7.3) makes the customer solely responsible for and indemnifying against all "Agent Operations." The ambiguity itself is a caution.
- **The independence killer — account gate (verified first-hand, 2026-10-27):** "Every Swamp command needs a swamp-club.com account, except the exempt commands" (help/auth/`swamp start`). "The requirement applies to every repository, including one using only a local filesystem datastore and a `local_encryption` vault." Commands check in with swamp-club.com and cache an Ed25519-signed proof (14-day lifetime, refresh after 7 days); without a valid proof, unreachable/refused answers **block** (24-hour grace only on 5xx); CI must carry `SWAMP_API_KEY` + `SWAMP_SIGNIN_TOKEN` (shown once, no expiry); `swamp serve` and `swamp worker` are checked at start; a worker without credentials passes only via its serve's vouch. This makes "self-hosted" Swamp continuously dependent on a third party's availability and revocation — directly against Factory's "designed-for self-hosting (Factory manages Factory)" standing input.
- **Contribution/independence posture:** issue-driven, "We don't accept pull requests from external contributors — fork PRs are automatically closed"; own tracker (Lab); 2,603 tags, no GitHub releases, no CHANGELOG; public profile/leaderboard/CLI telemetry (opt-out) noted by an independent reviewer as governance quirks. Field-report gap: **none of the six posts mentions Swamp's license** — hands-on users have not priced this in.
- **Cost comparison.** *Build on Swamp:* AGPL copyleft on any distribution + the "practical substitute" ceiling on extensions + closed registry/hosted services + mandatory account gate + SLA indemnity — Factory would rent its substrate. *Copy the ideas:* free — patterns, vocabularies, and architecture are not copyrightable; the AGPL reaches the code, not an independent Go implementation; the manual and repo are readable primary sources. **Learning-for-free is not just cheaper; it is the only option compatible with Factory's independence constraints.**

### Verdict — adopt / adapt / avoid, per concept

| # | Concept | Recommendation | Reason |

**Explicit answer to the ticket's framing — build on Swamp, copy its patterns, or ignore it?** **Copy its patterns; do not build on it; do not ignore it.** Swamp is the closest prior art to Factory and its production execution model corroborates closed/011 rather than threatening it. Building Factory on Swamp would trade the decided Go core, tracker neutrality, enforced capability control, SSH deploy, and unconditional self-hosting for a mature platform whose account gate and license put a third party in the loop of every run. Ignoring it would forfeit the three genuinely new ideas it brings: the YAML+JSON-Schema agent-authoring frontend, the default-deny grant model, and the skills+CLI harness seam.

### Impacts on the map

- **006 (harness substrate) — reshape, do not re-open.** This ticket adds a third candidate the grilling must name explicitly: the **harness-neutral CLI+skills orchestrator** (Swamp's seam), plus the rejected-for-core variant **"Factory as a Swamp behavior pack"** (feasible for milestone 1's loop per `@swamp/software-factory`, but no capability control, no tracker/PR integration, inherits account+AGPL). Recommendation: keep 002's hybrid as the base and require the spec's interop surface to be skills+CLI shaped, so the embedded runtime stays swappable.
- **009 (capability control) — reshape.** Feed it Swamp's grant model as the concrete reference model: default-deny, deny-wins, actions × resource selectors × CEL conditions (with cost budgets), groups, `--restricted-model-types/commands` as always-ask, `--approve-requires-explicit-grant` as separation of duties, per-workflow vault allow-list as per-workflow override. 009's question should test "profiles = named grant bundles" against the owner's lean.
- **010 (daemon vs CLI) — reshape.** Swamp proves both coexist (CLI primary + resident serve); give 010's sketch the concrete serve requirements harvested here (single port, stateless clients, connect-out workers, heartbeat HA, TLS-off-loopback, single credential/datastore/policy owner, daemon-side proof refresh). Strengthens "sketch both"; no re-open — it was always decide-later.
- **closed/011 (typed graph + CEL) — no re-open; one forward note.** No reopen trigger fires: Dhall conformance is unchanged, and Swamp's YAML+CEL DAG *is* the decided shape in another implementation. The one addition worth carrying: the successor ergonomics ticket (after 008) should prototype a **YAML/JSON-Schema frontend over the same IR** beside Dhall, using Swamp's `describe --json`/`validate`/`search --json` surfaces as the ergonomics bar. Recommended as a note on 008's follow-up, not a 011 re-open.
- **Fog cross-references (no new tickets):** the observability-schema and deploy-pipeline fogs each gain borrowable patterns (audit split, data lifetimes; worker enrollment/placement if per-machine executors ever appear) — main session's call whether to record that on the map.
